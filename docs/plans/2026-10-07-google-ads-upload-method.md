# Addendum: selectable upload method + optional developer token (Google Ads)

Status: **plan for review (no code yet)**. Extends `2026-10-05-google-ads-conversions.md` (read its "As-built deviations" first).

## 1. Why

Facts verified against Google's docs on 2026-10-07:

- **Developer tokens were sunset on 2026-09-09.** API access levels (Test / Explorer / Basic / Standard) belong to the **Google Cloud project that owns the OAuth client**. The `developer-token` header is optional and ignored by Google (`developers.google.com/google-ads/api/docs/api-policy/developer-token`).
- **`UploadClickConversions` (the v1 path) is restricted:** developer tokens with no offline-conversion upload between 2025-12-17 and 2026-06-15 get `CUSTOMER_NOT_ALLOWLISTED_FOR_THIS_FEATURE`; Google says the restriction "remains in effect" after the token sunset but does **not** say how it maps onto projects (`.../docs/deprecations`, `.../docs/conversions/upload-clicks`). Data Manager `events:ingest` has no such restriction.
- v1 uses the legacy API with the `adwords` scope only. v2 uses Data Manager (`adwords` + `datamanager`).
- The owner wants: keep Data Manager as the default, but allow the v1 way (legacy upload, `adwords` only, optional token) where Google still permits it. A **new** project (e.g. `ahamake`) cannot use legacy.

Non-goals: automatic fallback between methods; per-workspace choice; removing Data Manager; changing dedup, timing, state machine semantics.

## 2. Decisions

| # | Decision |
|---|---|
| U1 | New platform credential field `uploadMethod: "dataManager" \| "legacy"`. Absent (all rows saved before this change) = `dataManager`. Non-secret; included in the public projection. Chosen by the platform admin (or the reseller on their own credential), **not** inferred from whether a developer token was typed. |
| U2 | `developerToken` becomes **optional** in `googleAdsCredentialSchema` / update schema. Sent as `developer-token` only when present. `isConfigured` needs `clientId` + `clientSecret` only. The `developer_token_*` failure causes stay (Google may still report them); `developer_token_missing` is no longer raised by us. |
| U3 | Required OAuth scopes depend on the method: `dataManager` → `adwords` + `datamanager`; `legacy` → `adwords` only. The authorize URL requests only what the method needs. |
| U4 | The method in force for a connection is captured at connect time into `auth.metadata.uploadMethod` (jsonb, **no migration**) and read from the already-loaded auth at delivery. A connection without it = `dataManager`. Changing the credential's method affects new connections; existing ones keep theirs until reconnected (documented; the settings card shows the method). |
| U5 | Transport abstraction inside `integrations/google-ads`: `ingestEvent` routes by `auth.metadata.uploadMethod` to `dataManagerIngestEvent` (existing) or new `legacyUploadClickConversion`. Both return `{ requestId: string \| null; completed: boolean; fieldWarnings: unknown[] }`. Legacy: `completed = true`, `requestId = String(jobId)` (Google returns `jobId` for the upload). Data Manager: `completed = false`. |
| U6 | Business delivery stays method-agnostic: after a successful ingest, `completed === false` → existing `sent` + poll path; `completed === true` → the event goes straight to `processed` (`processingStatus: "success"`, no poll). The `(status IN sent/processed ⇒ requestId AND sentAt NOT NULL)` CHECK is satisfied by `requestId = jobId`. A partial failure in the response → terminal `failed(delivery)` with a sanitized message. |
| U7 | Legacy request (POST `customers/{conversionCustomerId}:uploadClickConversions`, headers `Authorization`, optional `developer-token`, `login-customer-id` per the existing login-account rule): `{ partialFailure: true, validateOnly?, conversions: [{ gclid \| gbraid, conversionAction: "customers/{cid}/conversionActions/{id}", conversionDateTime: "yyyy-mm-dd HH:mm:ss+HH:mm", conversionValue?, currencyCode?, orderId: <our transactionId> }] }`. `orderId` is the dedup key (≤ 128 chars, our ids already are). Response `{ results, partialFailureError?, jobId }`. Uses v25 like the rest of the integration. |
| U8 | `CUSTOMER_NOT_ALLOWLISTED_FOR_THIS_FEATURE` on a legacy upload (or on `validateIngest`) maps to a new failure cause `legacy_upload_not_allowed` with a translated message telling the admin to switch the credential to Data Manager. |
| U9 | Reuse everything else unchanged: timing (6 h, 90 d), D8 dedup ids, fenced lease, sweeper, UI event history, flow step/trigger action, `validateIngest` (legacy uses `validateOnly: true`). |
| U10 | Admin card (`platform-credentials/google-ads`): a select "Upload method" (Data Manager (recommended) / Legacy upload API) with helper text (legacy only works for Cloud projects Google still allows; no `datamanager` scope), developer token label "(optional)". Preserve-on-blank semantics for secrets unchanged; `uploadMethod` is a normal field. |

## 3. Work breakdown (tests first)

1. **Credential** (`packages/database/src/partials/credential.ts`): add `uploadMethod`, make `developerToken` optional (+ update/public schemas); old rows still parse. Tests in `packages/database/__tests__/credential.test.ts`.
2. **Integration package** (`integrations/google-ads`): scopes by method (`lib/scopes.ts`, `connection-auth.ts` required-scope check, `authorizeUrl`), store `uploadMethod` in `auth.metadata` at `exchangeCode` (from `input.credential.uploadMethod`), `legacyUploadClickConversion` (new `apis/legacy-upload.ts`), router in `ingestEvent`, `developer-token` header optional everywhere (`adsHeaders`), failure cause `legacy_upload_not_allowed`. Real-HTTP fake-server tests (extend `__tests__/wire-*.test.ts`): legacy body exact match, response with `jobId`, `partialFailureError`, 403 `CUSTOMER_NOT_ALLOWLISTED_FOR_THIS_FEATURE`, optional header, scope sets per method.
3. **Business**: `resolveDeveloperToken` returns optional token (no `missing` state); `isConfigured` = id+secret; delivery handles `completed` (finish straight to `processed` via a repository method that sets `status='processed'`, `processingStatus='success'`, `requestId`, `sentAt`); `validateIngest` passes through. Tests: both transports at delivery level, partial failure, idempotent redelivery.
4. **Builder**: admin card (select + optional token), connect error message for the new cause (exhaustive `connectErrorKey`), settings view shows the connection's method (small muted text), i18n in 21 locales. Tests.
5. **Docs**: `docs/google-ads-conversion-tracking.md` (methods, scopes, when to pick legacy, token optional), plan "As-built deviations".

## 4. Risks and open points (reviewers: challenge these)

- **R1:** how Google applies the legacy restriction to a *project* after the token sunset is undocumented. Mitigation: legacy is opt-in and clearly labelled; failures surface as `legacy_upload_not_allowed`.
- **R2:** legacy is on Google's deprecation path; the abstraction keeps removal to one file + one enum value.
- **R3:** `auth.metadata.uploadMethod` lives in the plaintext satellite `auth` (already the case for scope/customer metadata); it is not secret.
- **R4:** connections created before the change have no `uploadMethod` → `dataManager` (current behaviour). Switching a credential to `legacy` requires reconnecting existing workspaces; the UI says so.
- **R5:** `orderId` collision semantics differ from Data Manager `transactionId` adjustments (legacy treats a repeated `orderId` as a duplicate, not an adjustment) — confirm that is acceptable for our D8 rules.
- **R6:** per-event result of a legacy upload with `partialFailure: true` is in `partialFailureError`; the sweeper/retry must treat a partial failure as terminal (not retry) unless Google reports a transient code.

## 5. Review outcome (Codex gpt-6.1-sol, 2026-10-07) — BINDING changes; they override §2/§3 where they differ

Verified against official docs by the reviewer: token sunset facts; legacy needs `adwords` only; REST route/camelCase body match U7; `jobId` is an int64 serialised as a JSON string; `partialFailureError` is a `google.rpc.Status`; failed result entries are empty and `validateOnly` returns no results; `ONE_PER_CLICK + gbraid` is refused by the legacy API too (keep the existing refusal for BOTH methods; keep the external-attribution exclusion; consent stays a documented omission, never fabricate GRANTED).

## 6. As-built (steps A-C, 2026-10-07)

- Implemented in the binding order A -> B -> C; nothing committed. Full behaviour, scope table, legacy semantics and the retirement policy are in `docs/google-ads-conversion-tracking.md` ("Upload methods").
- **Step C deviations/notes:** (1) the settings projection (`GoogleAdsSettingsView.uploadMethod`) normalizes `auth.metadata.uploadMethod` inside the builder's `to-settings-view.ts` with the database `googleAdsUploadMethodSchema` (absent/unknown = `dataManager`) instead of calling a business helper: the builder does not depend on the integration package and importing business values breaks the node-env projection test; `auth` itself still never reaches the client. (2) The event resource gained `uploadMethod`; the history labels legacy rows only (Data Manager rows stay unlabelled to keep the table quiet). Legacy `processed` rows carry `processingStatus = success`, so the UI shows "Processed / Accepted" and never the "Google is processing" state. (3) `developerTokenMissing` / `developerTokenNotApproved` i18n keys and `developer_token_*` cause keys were kept, only the wording changed (21 locales): the token is optional, the missing-credential messages now name the OAuth client ID/secret, and the not-approved message says to remove or replace the optional token. (4) No new mutation or query was added, so no new TanStack invalidation is needed; the connection row still invalidates on connect/reconnect/disconnect/sync. (5) The admin hint under the Google Ads callback URL still mentions the `datamanager` scope for the OAuth app; it is accurate for Data Manager (the default).
- Open: R1 (project eligibility for legacy) remains unverifiable without a live Google check.
