# Posts (post management)

The **Posts** menu lists the posts that exist on a workspace's inbox channels (Messenger Pages, Instagram, Threads, TikTok), lets members organise them with topics, and controls how **new comments** on each post are handled. Composing and publishing posts from ChatbotX is covered from "Composed posts" on.

## What it does

- **List.** Filter by channel and inbox, post type, comment settings, engagement, topics, author and date; search by caption, link or exact post id; sort by newest, comments, phone numbers, engagement or shares. By default only posts that have comments are listed, plus posts published from ChatbotX (they always show, even with no comments yet); a post whose listing reports no comment count (Facebook Reels: the comments bit of `metricsKnownMask` is unset) also shows when a commenter is recorded for it in `ContactInboxPost` (looked up by `(workspaceId, postId)`); `hasComments=false` lists every synced post.
- **Topics.** Free-form labels (`PostTopic`) attached to posts. Up to 20 per post and 200 per workspace.
- **Per-post comment settings** (apply to comments that arrive *after* the switch is turned on; existing comments are not changed):
  - `hideComments` hides every new comment.
  - `hidePhoneComments` hides every new comment that carries a phone number.
  - `skipComments` marks every new comment as read. Comment Automation still runs.
  - Only channels whose `POST_CHANNEL_CAPABILITIES[channel].commentSettings` is true enforce them (Messenger, Instagram). Threads and TikTok do not track posts per commenter yet, so the switches are disabled for them (Threads still records a bare post row when a comment arrives, only to count it; see Fresh counts on view).
- **When the settings apply.** The settings are applied when a comment is processed, including a webhook re-delivery of a stored comment, so a retry that runs after a switch was turned on applies it (this keeps a hide from being lost when the first run stopped before enqueueing it).
- **Live comments.** A per-post hide (hide all, hide phone comments) is not applied to a live comment on a channel whose live rules refuse hiding (`liveCommentCapabilities(...).hideComments`: Instagram Live comments cannot be hidden, the same rule a Live comment automation follows); the comment is left visible, no hide job is queued and no message is charged. Skipping the comment, the phone count and the post triggers still apply. Facebook live comments are ordinary Page comments and are hidden as usual. `receiveComment` passes whether the comment is live to `applyPostCommentSettings`.
- **Message quota.** The hide and skip settings consume the account's message quota (`messageUsageService`, the owner pool a chat send uses, invariant 12): 1 message per comment a setting **hid** (after the provider accepted the hide) and 1 per comment a setting **skipped** (when the read mark really advanced). Comment Automation moderation hides, unhides, likes and every other `changeChannelMessageState` job are never charged: only the hide job queued by `enqueuePostHide` carries `usageSource: "postCommentSetting"`. At the limit the worker does not hide and does not skip the comment (it stays as it arrived; the skip is not retroactive after a top-up) and logs it at most once per post per hour. The charge is idempotent through a strict marker on the stored comment (`attributes.quotaChargedHide` / `quotaChargedSkip`, a conditional set-if-not-set that propagates a shard failure, like `phoneCounted`): the marker is claimed first, then 1 message is charged; the charge throws only when nothing was counted (the workspace could not be read); then the marker is released, so a retry charges and a redelivery never charges twice. Once a counter is written, a failing counter is logged and not repeated (a retry would count the other counters twice). Rule: never charge twice; a crash between the claim and the charge, or a database error during the charge, can lose that one charge. A failing hide charge fails the job (the hide is repeated and charged on retry); a failing skip charge is logged and never fails the comment's ingestion, and it is not retried: a redelivery finds the read mark already advanced, so that skip stays uncharged.
- **Phone count.** `phoneCommentsCount` is counted at most once per comment: the stored comment is marked (`attributes.phoneCounted`, an atomic set-if-not-set) and only the call that set the mark increments. Messages and posts live in different databases (messages are sharded), so the two writes cannot be one transaction and the count cannot be exactly-once. The design picks the safe side: when the increment fails the mark is **not** taken back (the outcome of a timed-out write is unknown, and undoing the mark could count the comment twice), so the count may **fall short**, never run over. Counting is best effort on the comment path: a failure is logged and never fails the comment job, so the steps that run once per new comment (leaderboard scoring, automations) are never skipped by a retry. **Repair:** refreshing one post (the refresh button / `POST …/{id}/refresh`) recounts its comments that carry a phone number from the messages (bounded at 10,000; a post above that keeps its number) and *sets* the stored count; the periodic sync does not. An increment landing between that read and write can be overwritten and is repaired by the next refresh. Anything that writes a message's `attributes` must patch only its own keys with a JSON merge: the like/hide job does (`patchMessageAttributes`), so a mark written meanwhile survives.
- **Phone-number rule.** One shared predicate, `hasPhoneNumber` (`packages/utils`), is used by hiding, counting and filtering, so the numbers always agree. It is deliberately loose (a run of eight or more digits and separators), so a long date or a price written with dots can match.
- **Sync.** Posts are listed from each channel by a background job, not on every page open. The Posts page polls the sync status every 5 s while any inbox is queued or running and refreshes the list once it settles.

## Sync engine

- `LowJobAction.syncChannelPosts` on the `low` queue, started by `POST /v1/channel-posts/sync` or by the minute cron `scanChannelPostSyncs`, which picks due rows with `FOR UPDATE SKIP LOCKED`.
- A run claims the row with a conditional UPDATE and a `claimToken`; every later write (progress, release, failure) is conditional on `(id, claimToken, status = 'running')`, so a run that was taken over stops writing.
- Each run handles at most 5 pages or 60 seconds, saves the resume cursor, and the cron schedules the next run. A page and the fenced position write are **one transaction** (`commitPage`): a worker that was taken over touches no row, so its page is rolled back and it stops; it can never overwrite newer metrics. Thumbnails are downloaded after the commit. A cycle stops at 2,000 posts; the periodic re-sync is every 6 hours; the refresh button rests 60 seconds per inbox.
- The upsert writes metrics only when they differ and never touches the three switches, `phoneCommentsCount`, or an existing thumbnail. A value the listing leaves out (null caption, permalink, publish time, content type, live status, author, a count) keeps the stored one; a stored `reel` is not turned back into `video` by a single-post lookup, which cannot tell a Reel apart.
- **A failed run keeps its place.** The saved resume cursor is dropped (the listing starts again from the newest page) only when the channel rejects, as invalid, the cursor loaded from the claim on the first read of the job (`ChannelError` `payload_invalid`; the Messenger cursor that cannot be decoded raises that too); a rejection on a later page of the same job keeps the pages already written. Any other error, a database or network failure included, retries from the saved cursor, so one blip does not restart a long first listing.
- **The refresh button reads now.** `POST /v1/channel-posts/management/{id}/refresh` (private twin: the post sheet and row menu) reads the post from its channel inside the request, bounded by 15 seconds, and answers `{ outcome, post }`: `refreshed` (counts written, `post` is the updated item), `removed` (the channel confirmed the post is gone; `post` is null), `channelUnavailable`, `rateLimited` or `cooldown` (the post was refreshed in the last minute: a Redis window of 60 seconds per post, nothing is read). The steps are ONE function, `runChannelPostRefresh` (`@chatbotx.io/channel-registry/channel-post-refresh`, a server-only subpath so the channel code stays out of the builder's Edge instrumentation graph): phone-count repair, live-state re-read, `getPost`, the fenced `recordPage` write, `NOT_FOUND` -> `markPostRemoved`. The `refreshChannelPost` low job calls the same function for its other callers (after a publish, live re-reads), with its own 60-second job id. The response still carries `queued: true`, deprecated and always true, so clients written for the earlier background refresh keep validating; read `outcome` and `post`.
- `removedAt` is set only after looking up that one post and the platform answers "gone" (only TikTok reports that unambiguously); a post that appears in a later listing clears it.
- **Only syncable inboxes sync.** One predicate (`postSyncEligible` in `repositories/channel-post-sync/repository.ts`) decides: the inbox is in the workspace, `Inbox.status = 'connected'`, AND the integration row of its channel (`IntegrationMessenger` / `IntegrationInstagram` / `IntegrationThreads` / `IntegrationTiktok`, matched by `inboxId` and `workspaceId`) exists. `findEligibleInboxes` (as `syncable`), `listForWorkspace`, `requestRefresh`, `queueDue` and `claim` all use it, so a connected inbox with no integration row is never listed, requested, queued or claimed. Earlier text, still true: A sync request creates rows and queues jobs only for inboxes with `Inbox.status = 'connected'` (a disconnected inbox is left out of the answer); the minute scanner (`queueDue`) and the per-inbox claim both check the inbox with an `EXISTS` on its primary key, so a row whose inbox was disconnected is never queued and a job that finds it disconnected returns without writing a failure. Existing rows are kept, so reconnecting the inbox lets the next request or scan pick it up again.
- **Not connected is not a failure.** When the channel has no integration for the inbox (the registry's `ChannelError` with code `integration_auth_missing`), the run puts the row back to `idle` with no `nextSyncAt`, clears the retry count and sets `lastErrorCategory = 'notConnected'`. It is not `failed`, not retried, and waits for a new sync request. The public sync status lists only syncable inboxes, so a parked row is not returned.
- **Posts page.** The sync status list holds only syncable inboxes; real `failed` syncs show as one compact notice ("N pages could not sync") with a toggle listing each inbox (`lib/sync-failures.ts`). `notConnected`, disconnected, integration-less, queued and idle rows are never shown. Per `lastErrorCategory`: `auth_failed` → "Reconnect the channel" (link to the Connect tab); `permission_denied` → "Reconnect and allow post access"; any other terminal error → a "Try again" button that requests a sync for that inbox.
- **Self-heal (minute scan, bounded to 50 rows per step).** Before queueing, `scanDue` (1) parks `failed`/`idle`/`queued` rows whose inbox is not syncable as `idle`, no `nextSyncAt`, no error, `lastErrorCategory = 'notConnected'` (repairs legacy failed rows with no migration), and (2) makes `auth_failed`/`permission_denied` rows of syncable inboxes due again only when the integration row's `updatedAt` is newer than the row's (a re-authorisation or token refresh; a stop-gap signal), so a permanent auth failure is not retried otherwise.
- **Reconnect resets the sync.** A reconnect with **new credentials** fully resets the sync through `resetChannelPostSyncAfterAuthChange` (`channelPostSyncService.resetAfterAuthChange`), in the same transaction as the write: a `failed` row, or one parked as `notConnected`, becomes `idle`, due now, with error, attempts and lease cleared (a queued or running row is left alone). The places: `connectionStateService.commitReconnect` (token refresh / reauthorise), `connectionStateService.transition` for `connect.completed` on an inactive-to-active edge (Settings → Channels → Add reuses the disconnected `Inbox` row through the connection engine), and `inboxService.create` reviving a disconnected inbox (legacy path).
- **Resume without new credentials** (`teardown.resume` on a paused connection, `inboxService.resumeTenantSuspended`) only releases a row parked as `notConnected` (`releaseParkedChannelPostSync`); a `failed` auth or permission row stays failed and is left to `releaseRecoveredAuthFailures` (integration row must have changed). Connected/degraded flaps and no-op re-assertions never touch the sync.
- **Self-heal also releases parked rows.** As a safety net for any path that re-activates an inbox without the reset above, the minute scan makes `idle` / `notConnected` rows due again (`releaseReconnectedParked`, bounded to 50) once their inbox is `connected` and its integration row exists (served by the partial index `ChannelPostSync_parked_notConnected_idx`). It runs after `parkIneligible`, so a row is never parked and released in the same scan.
- Failures: rate limit → push `nextSyncAt` back; auth or permission → `failed`, no retry until re-authorised; transient → up to 5 attempts.

## Post author

The list, the detail panel and the author filter use two columns, `authorName` and `authorExternalId`, filled only when a channel reports an **individual** creator. `POST_CHANNEL_CAPABILITIES[channel].author` says which channels do.

| Channel | Author reported | Source |
|---|---|---|
| Facebook (`messenger`) | `admin_creator{id,name}` on the Page's `/posts` edge and on a single post, when present | Graph API reference "Page Post" (`/docs/graph-api/reference/page-post/`): `admin_creator`, type `BusinessUser\|User\|Application`, "Only available if there exists more than one admin for the page"; the Page feed reference says it is null for a regular post. No extra permission is documented for the field. |
| Instagram | none: media `owner` / `username` is the connected account itself | "IG Media" reference (`/documentation/instagram-platform/reference/instagram-media`): `owner` is only returned when the app user also created the media, `username` is the user who created it |
| Threads | none: `username` / `owner` is the connected account | "Retrieve user posts" (`/documentation/threads/retrieve-and-discover-posts/retrieve-posts`): "Username of the Threads user who created the post" |
| TikTok | none: the video list returns the connected user's own public videos | "List Videos" (`/doc/tiktok-api-v2-video-list`) |

- A single-admin Page, or a regular post, has no `admin_creator`; that is the normal case, not an error, and leaves both columns empty. A later sync that cannot read the field never erases a creator already stored (the upsert keeps the old value when the new one is null).
- **Retry-without-field rule.** `admin_creator` is requested with the post fields. If Graph answers with error 100 (invalid parameter), 200 (permissions error) or 283 (requires extended permissions), the same page is requested once more without the field, with the same cursor, so the sync loses no page and its cursor does not move. Any other error, or the same error on the retry, propagates as before. The Reels edge (`video_reels`) is not asked for the field: the Page Post reference does not return Reels and the Video Reels edge reference lists no creator field.
- **Display rule.** The web always shows an author. With a creator it shows the name; otherwise it shows the inbox (Page or account) name with a muted "Page" (Facebook) or "Account" (other channels) tag so it is not mistaken for a person (`resolvePostAuthor`, `post-author-label.tsx`). The author filter lists only real creators (`authorExternalId` present) and does not render when there are none. `listAuthors` returns one row per (inbox, author) with `authorKey` (`<inboxId>:<authorExternalId>`), `inboxId`, `inboxName` and `channel`, so the same person on two pages is two options; the web labels each "Name · Page" with the channel icon and its search also matches the page and channel name. `authorIds` accepts an `authorKey` (that author on that inbox only) or, as before, a bare `authorExternalId` (every inbox). The page and account pickers show the channel icon too, and the Post type list offers Past live and Live now only when a connected inbox's channel reports live status (`POST_CHANNEL_CAPABILITIES[*].live`: Facebook; see "Live status"), and the merge dialog's "went live in the last 3 hours" pre-selection is off without it.
- Not verified: which access token or permission Facebook needs for `admin_creator` (none is documented, hence the fallback above).

## Comments of a post

The comments window, the merge view and the exports read the comments of one or up to 20 posts through `channelPostCommentsService` (`packages/business/src/channel-post/comments.service.ts`). `openReader` resolves the posts and their threads **once**; every page after that runs only the message query plus one lookup of that page's commenters.

- **Threads.** A post's comments sit on one conversation per commenter, all with `sourceId = externalPostId`. One query finds them for every post of the read (partial index `Conversation(workspaceId, sourceId, lastActivityAt DESC NULLS LAST, id DESC)`, which carries the read order so one post's threads need no sort); the post's inbox is checked with a correlated semi-join (`EXISTS` on the contact's `ContactInbox`), so a contact with several rows in the inbox still yields each conversation once before the cap. A post id belongs to one inbox of a channel (the page, Instagram, Threads or TikTok account id each have their own global unique index), so the inbox check is defensive, not a way to tell apart two inboxes sharing a post id. At most the 5,000 most recently active commenters are read **in total** (`MAX_COMMENT_THREADS_PER_READ`), not per post.
- **Inbox exactness.** The reader then fetches the contacts' `ContactInbox` rows in the posts' inboxes (one query, array parameters), reads messages only where `contactInboxId` is one of them, and attributes each comment to the post of its contact inbox's inbox. A contact merged across inboxes A and B therefore shows a post only the comments sent through that post's own inbox.
- **Messages.** Newest first through `(workspaceId, conversationId, type, createdAt)` with a keyset cursor that carries the exact microsecond timestamp (a `Date` would skip or repeat rows created in the same millisecond). The id lists (`conversationId`, contact ids) are bound as ONE `bigint[]` parameter (`= ANY($n::bigint[])`), so a read over any number of threads stays far under the protocol's 65,535-bind limit.
- **Filters.** `search` is a case-insensitive contains with LIKE wildcards escaped (a caller without phone permission searches the text with numbers masked, see below); `hasPhone` filters in SQL with the same rule as `hasPhoneNumber` (`PHONE_NUMBER_SQL_PATTERN`, pinned equal to the JavaScript rule by a test against PostgreSQL).
- **Replies.** `parentCommentId` is the `id` that the parent comment has in this list (its own message id), not the channel's id.
- **Phone data.** A member needs the `emailAndPhone` permission; an API token follows the policy shared with the broadcast API (`TOKEN_CALLER_CAN_VIEW_EMAIL_AND_PHONE`). Without it the commenter's phone is null, phone numbers inside the text are masked, and `hasPhone` is refused (422), because it would reveal which comments carry a number. A text `search` is allowed but runs over the **masked** text (`regexp_replace(text, <phone pattern>, '•••', 'g') ILIKE …`, pattern and search both bound parameters), so a number can never be probed, with separators or without, while an ordinary search such as "2026" works. The SQL mask also takes the space after a number, which the JavaScript mask gives back.
- **Like and delete** reuse the inbox path. Like queues `changeChannelMessageState`. Delete queues `deleteChannelMessage` **first**, with the fixed job id `delete-comment-<messageId>`, and only then soft-deletes the inbox row and emits `messageDeleted`; if the queue is down the call fails and the comment stays (a retry reuses the job id, so the channel delete runs once). Like is never offered for Instagram (the like endpoint of the Instagram connector is not in the official reference; the comments window hides the heart and the like procedure answers 409 `commentActionUnsupported` without calling the network; Messenger/Facebook and TikTok keep it, Threads has none). Both are allowed only per `POST_CHANNEL_CAPABILITIES[channel].commentLike` / `.commentDelete` (Messenger and TikTok both; Instagram delete only; Threads neither) and answer 409 `commentActionUnsupported` otherwise. The comment must sit in one of the post's own threads and in the post's own inbox.

## Live status

`ChannelPost.liveStatus` (`live` while a broadcast is on the air, `ended` once it is over; the enum also has `scheduled`, which no source writes) is set by the signals below and shown by the Live now / Past live filters and the live badge. Only **Facebook** reports it (`POST_CHANNEL_CAPABILITIES.messenger.live = true`). `instagram` stays `false`: only the Facebook-Login connection can list (`live_media`) and end a broadcast, the Instagram-Login connection has no end signal (`live_comments` stops when the broadcast ends and nothing else says it ended), so a channel-wide flag would promise a lifecycle half of the accounts cannot complete. Instagram-Login comments never write a live status (a row that could never end would be stuck on live); Instagram-Facebook-Login rows do carry it in the public API (`liveStatus` filter and field).

**One guarded write.** Every signal goes through `channelPostRepository.recordLiveObservation` (`channelPostService.recordLiveObservation`): an upsert on the post's unique key (workspace, channel, external post id) that sets `liveStatus`, `liveStatusObservedAt` and `contentType = 'live'` (only when the stored type is unknown or a plain `video`; a Reel stays a Reel). It applies only when `liveStatusObservedAt` is null or older than the observation (an older reading never overwrites a newer one), and a `comment` observation is weak evidence: it may start a live status on a row that has none and may end one, but never reopens an ended broadcast and never refreshes a live one. Observation times are taken before the read, so a slow write is not mistaken for newer.

**Sources (Facebook).**

| Source | What it does |
|---|---|
| Comment | The comment lookup that already runs per comment (`getCommentAttachment`, field `live_broadcast_timestamp`, then `object{live_status}` of the commented video) now also reports the broadcast state: `LIVE` is live, `LIVE_STOPPED` is ended, a failed or empty video read is `unknown` and records nothing. No extra Graph call. |
| `live_videos` webhook | The Page field (already subscribed) enqueues `liveVideoStatusChange` (job id `live-video-<id>-<status>`, `low` queue, 3 attempts). The worker reads `GET /{live-video-id}?fields=id,status,title,description,creation_time,broadcast_start_time,permalink_url,video{id,post_id,live_status}` with the Page token and records what the read says (never the webhook's status), source `webhook`. The post id is `video.post_id` as returned; a broadcast without one is logged and skipped (ids are never concatenated). |
| Sync (Sync button and the periodic sync) | The listing reads `video_reels`, then `/{page}/live_videos` (every broadcast the Page has, past ones included, paged with the same cursor and the same 2,000 post cap), then the feed. The edge is asked with the documented `broadcast_status=["LIVE","LIVE_STOPPED","VOD","PROCESSING"]` (without the param it returns every status; ended broadcasts are returned, VERIFIED), so scheduled and unpublished ones are not fetched. One table (`liveBroadcastStatuses` in `integrations/messenger/src/apis/live-video.ts`, shared by the sync, the webhook job and the state read): `LIVE` / `LIVE_NOW` are `live`; `LIVE_STOPPED`, `VOD`, `PROCESSING` are `ended`; `UNPUBLISHED`, `SCHEDULED_*` (including `SCHEDULED_EXPIRED`) and any unknown value record nothing (never defaulted to ended). A broadcast that is also in the feed is **one row**: both use `video.post_id`, a later feed page does not turn `live` back into `video` and a listing with no live status never clears a stored one. A listing's status replaces a stored one only if it was read after the last observation (`liveStatusObservedAt`). A token that cannot read the live edge skips that pass (logged) so the feed still syncs. |
| Re-read of live rows | `ChannelPost.liveRecheckAt` is the schedule (not `liveStatusObservedAt`): every live observation or live listing sets it 10 minutes ahead; an ended one clears it. Each minute scan **claims** up to 20 due rows in one statement (`claimLiveRechecks`: `FOR UPDATE SKIP LOCKED`, oldest due first, served by the partial index `ChannelPost_liveRecheckAt_id_idx` on `(liveRecheckAt, id) WHERE liveStatus = 'live' AND liveRecheckAt IS NOT NULL`, so the limit bounds the rows examined) and moves each one's `liveRecheckAt` 10 minutes ahead before any integration is looked at; a broadcast that started more than 24 hours ago, or a removed post, has it cleared instead and is not re-read. A row whose integration is gone or whose re-read fails therefore goes to the back of the line and cannot starve other workspaces. Claimed rows go to the existing `refreshChannelPost` job, which asks the channel's `getLiveState`: `live` or `ended` is recorded (source `reread`); `unknown` or a failed read leaves the status alone (the next try is the claim's next window). After 24 hours a row nobody settled is left as it is. |

**Instagram (Facebook Login).** `live_comments` marks the post as live (comment evidence). The sync lists `GET /{ig-user-id}/live_media` first (it returns only the media being broadcast at request time) as `live`. A **past Instagram live cannot be listed**, so only a broadcast seen while on the air ever becomes `ended`: the stale re-read calls `getLiveState`, which answers `ended` only after a successful, fully read `live_media` answer that does not list the media (a long list or a failed call is `unknown`/an error, never `ended`). The pass is skipped, logged, when the token cannot read `live_media`.

- Video `live_status` values (the comment lookup relies on `LIVE` and `LIVE_STOPPED`, observed, not listed by the reference; any other value is treated as not a live video).
- Whether the `LiveVideo.status` node field ever reports `LIVE`, `LIVE_STOPPED`, `VOD` or `PROCESSING` (the reference documents them for the `broadcast_status` filter and lists `LIVE_NOW` for the node); both spellings are mapped.
- The order of `live_videos` (assumed newest first) and that `video.post_id` equals the id the feed and the comment webhook use.
- Instagram Login (`graph.instagram.com`) `live_media`: not called.

**Deploy.** The `live_videos` edge needs a Page access token, `pages_read_engagement`, `pages_show_list` and the app's "Live Video API" feature (official reference, v27.0); without them the live pass is skipped and logged and the feed still syncs. `live_videos` is in the Page webhook fields the app already subscribes (`integrations/messenger/src/apis/page.ts`); pages connected before that field was added are re-subscribed by `apps/worker/scripts/resubscribe-messenger-webhook-fields.ts`. Migrations: `liveStatusObservedAt` and `liveRecheckAt` are columns of the posts-management migration; `ChannelPost_workspaceId_liveStatus_sortAt_id_idx` (partial, `liveStatus IS NOT NULL`, the default list order) and `ChannelPost_liveRecheckAt_id_idx` are built `CONCURRENTLY` in the follow-up index migration. The first sync after the release brings past broadcasts in. The per-post hide setting skips a hide that the channel's live rules refuse (an Instagram Live comment is never hidden, same rule as a Live comment automation); skipping, the phone count and triggers are unchanged.

## Exports

`channelPostExportService.build` writes a CSV of the comments of 1–20 posts. It opens one reader (posts, threads and all commenters looked up once) and pages only the message query; one page and the rows kept so far are held in memory.

- `kind=comments`: one row per comment, columns `createdAt` (ISO), `post` (caption, else the external post id), `customer`, `phone`, `text`, `hidden`.
- `kind=phones`: one row per customer who left a phone number, columns `customer`, `phone` (the contact's number, else the number written in the comment), `firstCommentAt`, `post`. It needs `emailAndPhone` permission and is refused with 403, never written partly, without it.
- Cells are escaped with the shared CSV helper (`packages/utils/src/csv.ts`): quotes doubled, line breaks flattened, a leading `= + - @` or tab prefixed with a quote.
- **Bounds.** The read stops at 20,000 comments (`MAX_EXPORT_ROWS`) or 20 seconds (`EXPORT_TIME_BUDGET_MS`), whichever comes first, and returns `truncated: true`. The 5,000-thread cap of the comment reader (`CommentReader.threadsCapped`) also sets `truncated: true` (and the `X-Export-Truncated` header), since commenters beyond it are never read.
- **Deviation from the plan.** The plan described a background export job with a stored file and a retention period. The export is deliberately synchronous instead: the file is built inside the request and returned in it, with the row and time caps above. A comment export is bounded (twenty posts at most, 20,000 rows), a stored file would hold customers' phone numbers and comment text for a retention period and need its own permission re-check on download, and the job, storage and cleanup machinery would be more to run than the exports are worth. If exports must exceed the caps, the job-and-file design in the plan is the way to extend it.
- **Message quota.** A completed download consumes 1 message of the account's quota (`messageUsageService`, invariant 12), the same for the session route and the public procedure because both go through `channelPostExportService.build`. Because it consumes a message, a workspace whose plan or trial has expired is refused: the public procedure with 403 `trialExpired` or `macLimitReached` by the token gate (the export path is not in the trial-expired read-only list), the session route with 402 `workspaceBlocked` by `assertWorkspaceNotBlocked` (it is a GET, so the gate lets it through); the Posts page shows a translated message. The session route is a cookie-authenticated GET that spends a message, so it serves only a same-origin request (`isCrossSiteRequest`, plus `Sec-Fetch-Site: same-site` refused): anything else answers 403 `crossSiteRequest` before reading or charging. With no message left it answers 429 `postMessageQuotaExceeded` before reading anything (the route returns `{ code }` with status 429; the Posts page shows a translated message instead of saving a file; the public procedure declares it in its errors). The charge is made once the file is fully built, right before it is returned (a truncated or empty file counts too); a request refused earlier (invalid ids, no phone permission, quota) or failing while reading charges nothing. A read where a message shard failed (the page carries `hasPartialResults`) fails the export with 503 `postCommentsUnavailable` and charges nothing, so a file is never silently missing comments. A crash after the charge and before the response is delivered still costs the message. Page downloads (row menu, detail sheet, header button) go through `fetch` (`useDownloadPostsExport`) so the 429 can be shown as a toast.
- **Posts-list export (`kind: rows`).** One CSV row per post (publishedAt, channel, page, type, text excerpt of 200 characters, comments, reactions, shares, phones count, topics, author, link, externalPostId) for the list filters, read page by page through `channelPostManagementService.list` (so it is exactly what the list shows, `hasComments` defaulting to `true`), capped at 5,000 posts and the same time budget (then `truncated`), same charge rule (1 message per file, 429/402/403 as above), same formula guard. The public procedure takes `filters` (the list request without `cursor`/`limit`, `sort` included) instead of `postIds` and refuses the combination; the session route takes the same filters as query parameters (`kind=rows&channels=…&sort=…`). The header export button is a menu: comments of the filtered posts (needs a date range) or the posts list. Row menus, detail sheet and header exports are disabled with a tooltip on a trial-expired workspace (the server refuses them); comment like is disabled there too, comment delete stays open (DELETE is not gated), and the row menu has check items for the three comment switches (same update operation as the detail sheet).
- Delivery: the public procedure returns the file in the response (`POST /v1/channel-posts/management/export`, which takes post ids; the Posts page header button lists the posts that match the current filters with the same list request as the page (`privateListManagedChannelPostsAPI`, public twin `GET /v1/channel-posts/management`) and needs both ends of the date range, takes the first 20 posts of that list (the export limit; it lists 21 to tell the user more match and says so) and downloads through the route below, so an agent gets the same result by listing with the filters and passing the ids; no separate export-by-filters procedure exists); the page downloads it from `GET /space/{workspaceId}/posts/export?kind=comments|phones&postId=…` (repeat `postId`; session + `broadcast` permission + `emailAndPhone` check; UTF-8 with a BOM for Excel, `Content-Disposition: attachment`, `no-store`, `X-Export-Row-Count`, `X-Export-Truncated`).

## Publishing destinations

Facebook Pages, Instagram and Threads publish with the **inbox's own integration token**: a workspace connects the channel once, as an inbox, and that connection is also the publishing connection. Nothing separate is connected for them, and connecting asks for no extra login. Only **TikTok** keeps a separately connected login (a *social account*, see "TikTok publishing"), because its publishing app differs from the inbox integration.

| Network | Token used | Destination id | Publisher (`PublisherKey`) | Permissions publishing needs (`PUBLISH_REQUIRED_SCOPES`) |
|---|---|---|---|---|
| Facebook Page | Page token of `IntegrationMessenger.auth` | `pageId` | `facebook` | `pages_manage_posts`, `pages_read_engagement`, `pages_show_list` |
| Instagram, Instagram Login inbox (`IntegrationInstagram.type = 'instagram'`) | `IntegrationInstagram.auth` token, `graph.instagram.com` | `igId` | `instagram` | `instagram_business_basic`, `instagram_business_content_publish` |
| Instagram, Facebook Login inbox (`type = 'facebook'`) | the same column, which holds the Page token, `graph.facebook.com` | `igId` | `instagramFacebook` | `instagram_basic`, `instagram_content_publish`, `pages_read_engagement`, `pages_show_list` (publishing); `instagram_manage_contents` is asked at connect too but is **not** a required publish scope (only a delete needs it, so a connection without it keeps publishing) |
| Threads | `IntegrationThreads.auth` token | `threadsUserId` | `threads` | `threads_basic`, `threads_content_publish`, `threads_manage_replies`, `threads_delete` |
| TikTok | `socialAccountService.getCredentials` (the separate login) | the destination's `externalId` | `tiktok` | `user.info.basic`, `video.publish` (`video.upload` is no longer requested: only Direct Post is used) |

Scope source: `instagram_business_content_publish` is the permission the Instagram Content Publishing documentation lists for Instagram API with Instagram Login (alongside `instagram_business_basic`); it is spelled as the platform spells it.

### Data

- `PublishDestination`: the binding every post target, target set, feed and posting schedule points at. Columns: `workspaceId`, `provider`, **either** `inboxId` (Facebook, Instagram, Threads; `ON DELETE CASCADE`) **or** `socialAccountDestinationId` (TikTok; `ON DELETE CASCADE`), `grantedScopes` (`text[]`, `NULL` = never captured), `publishStatus` (`ok` | `permissionMissing`, default `ok`), `missingScopes`, `statusTokenFingerprint`, `checkedAt`. A `CHECK` allows exactly one of the two references and ties `provider = 'tiktok'` to the social destination; each reference has a partial unique index, so an inbox or a TikTok destination has one binding.
- Rows are created **lazily and idempotently** (`INSERT … ON CONFLICT DO NOTHING`, at most 200 inboxes per network) when the destination list is read, when a post is created or updated with an `inboxId`, when a connect or reconnect captures scopes, and when TikTok destinations are merged. Disconnecting an inbox changes no row: its state becomes `inboxDisconnected` and it drops out of the pickers; reconnecting the same page reuses the inbox row, so the binding and the posts that point at it survive.
- `PublishDestinationSchedule`: the destination's weekly posting times (see "Posting schedule"), one row per destination.
- `SocialAccount` and `SocialAccountDestination` hold **TikTok only** (a `CHECK` pins `provider = 'tiktok'`): the encrypted tokens (`encryptUtils.encryptObject` with an AAD binding the ciphertext to its row), `grantedScopes`, `status`, `statusReason`, `tokenExpiresAt` and the refresh lease. They are never in a DTO, a log or a cache and are not copied by templates. Neither `PublishDestination` nor `PublishDestinationSchedule` is copied by templates (a binding is tied to a connected channel or login) and neither needs a Tools card.
- Foreign keys: `SocialPostTarget.publishDestinationId` is `RESTRICT` (the workspace purge drains targets first, `HEAVY_WORKSPACE_TABLES`); `SocialPostTargetSetDestination`, `SocialPostFeedDestination` and `PublishDestinationSchedule` are `CASCADE`, and the purge drains those dependents child-before-parent in bounded batches before the targets and the bindings.

### State of a destination

`derivePublishState` (`packages/utils/src/publish-destination.ts`) gives one of four states, first match wins:

| State | When | What the person does |
|---|---|---|
| `inboxDisconnected` | the inbox behind it is not `connected` | reconnect the channel; not offered in pickers |
| `needsReconnect` | the stored token was rejected or expired (`Integration<X>.tokenRefreshError` is set, for example `publishTokenRejected`; TikTok: the login is not connected or inactive) | **Reconnect** |
| `permissionMissing` | the network refused a publish for a missing permission (`publishStatus = 'permissionMissing'`), or a known `grantedScopes` list lacks a required scope, or an Instagram destination has no captured scopes | **Reconnect to allow publishing** |
| `ready` | none of the above (Facebook and Threads with unknown scopes publish until a network error says otherwise) | nothing |

Instagram with no captured scopes cannot be assumed to hold the content-publish permission, which older connects never asked for, so those inboxes read `permissionMissing` until they reconnect. Until Meta App Review approves `instagram_business_content_publish` and `instagram_content_publish` for the app, every Instagram inbox shows `permissionMissing`.

### Credentials at publish time

`loadPublishCredentials({ workspaceId, publishDestinationId })` is one repository read that joins the binding, the inbox and the integration, with a `workspaceId` predicate on every table. It returns the access token, the destination's external id, the `PublisherKey` and a fence (inbox: integration table, row id and the SHA-256 fingerprint of the token), or a typed blocker: `inboxDisconnected`, `inboxNeedsReconnect`, `publishPermissionMissing` (a failure that provably created nothing). The publisher is chosen by `PublisherKey`, so the two Instagram flavours use the same publishing code over two transports (`graph.instagram.com` and `graph.facebook.com`). An Instagram `continuation` records `via` (which flavour made the container); a recovery that finds the destination now publishes through the other flavour moves the target to `needsReview` rather than reading a container with the wrong token.

When a publish fails on the token, `recordPublishAuthFailure` reacts:

- `authFailed` (the token is invalid) sets `Integration<X>.tokenRefreshError = 'publishTokenRejected'` with a conditional UPDATE that applies only while the error is still unset and the stored token still matches the fingerprint the publish used, so a reconnect that happened meanwhile is never overridden. It **never** touches `Connection.status` (that would disconnect the inbox and release its quota). The existing token-refresh-error dialog renders the code.
- `permissionDenied` sets `PublishDestination.publishStatus = 'permissionMissing'` with the `missingScopes`, the token fingerprint and `checkedAt`.

A reconnect clears both: the reconnect write clears `tokenRefreshError` and resets the binding's status.

### Connecting and reconnecting

There is no Meta "connect a social account" flow. A workspace member connects the channel as an inbox (Facebook Page through the Messenger connect, Instagram, Threads); the Connect tab's buttons call the same reconnect actions of `integration-messenger`, `integration-instagram` and `integration-threads`, which take a `returnTo` argument (enum `postsConnect`) so the callback returns to `/space/<id>/posts/connect`. TikTok connects through `connectSocialAccountAction` (session only; an exempt OAuth step under invariant 23): a workspace super admin, `flow: "socialAccount"`, a single-use nonce in the OAuth `state` and an httpOnly cookie, the callback's `tiktok` branch (`completeSocialAccountConnect`) and `socialAccountService.connect`, which refuses with `permissionNotGranted` when a required permission was not granted.

**Scope capture** (stored in `PublishDestination.grantedScopes` at first connect and at every reconnect, from the platform's own answers; also re-read when the Posts Connect tab is opened, see below). Every row is from the official documentation pages, fetched for this section:

| Network | Source on connect | Source on re-check (Connect tab open) |
|---|---|---|
| Facebook Page | `debug_token` (`scopes`): "List of permissions that the user has granted for the app in this access token." Also `is_valid`: "Whether the access token is still valid or not." Needs "An app access token or an app developer's user access token for the app associated with the `input_token`". <https://developers.facebook.com/docs/graph-api/reference/debug_token/> | The same `debug_token` call with the stored Page token (`readTokenScopes`, `integrations/messenger/src/apis/token-scopes.ts`) |
| Instagram via Facebook Login | `GET /me/permissions` with the login's user token (`getGrantedPermissions`, granted entries only). The reference documents `GET /{user-id}/permissions`: "Returns a list of granted and declined permissions" (`status`: `granted`, `declined`, `expired`) and does not state which token type a read needs. <https://developers.facebook.com/docs/graph-api/reference/user/permissions/> | `debug_token` with the stored token. The stored token is the Facebook **Page** token (the user token is not kept), and `/permissions` is documented for a user id, so the re-check uses the documented `debug_token` instead (`integrations/instagram-facebook/src/apis/token-scopes.ts`) |
| Instagram Login (`graph.instagram.com`) | the `permissions` of the Business Login code exchange: the app receives "a list of the permissions granted by the app user" (accepted in the documented `{ data: [...] }` shape and the older flat one; an answer without it claims nothing) | **No documented source, not re-checked.** The long-lived exchange and the refresh answer only `access_token`, `token_type`, `expires_in`; the Business Login page documents no `debug_token` or permissions endpoint for Instagram User tokens. <https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/business-login> |
| Threads (`graph.threads.net`) | not reported by the platform: stored as unknown (`NULL`) and treated as ready. The code exchange answers `access_token`, `token_type`, `user_id`; the long-lived exchange and refresh answer `access_token`, `token_type`, `expires_in`. | **No documented source, not re-checked.** No `debug_token`, `/me/permissions` or other call to read a Threads token's permissions is documented. <https://developers.facebook.com/docs/threads/get-started/get-access-tokens-and-permissions> |
| TikTok | the token response `scope`: "A comma-separated list of the scopes the user authorized." <https://developers.tiktok.com/doc/oauth-get-a-user-access-token> | The refresh response carries the same `scope` field (<https://developers.tiktok.com/doc/oauth-refresh-a-user-access-token>); no other endpoint is documented. No Connect-tab call: the existing minute refresh scan (`refreshSocialAccountTokens`) now stores the refresh response's `scope` on `SocialAccount.grantedScopes` in the same fenced write as the new token. |

The table is code too: `PUBLISH_SCOPE_RECHECK_SOURCE` (`packages/utils/src/publish-destination.ts`, keyed by `PublisherKey`) names the documented re-check source (`debugToken` or `null`), and `createPublishScopeOps` (`packages/channel-registry/src/publish-scope-ops.ts`) maps each publisher to its reader; no channel-name conditions sit in shared code.

**Re-check on Connect tab open.** Pages connected before scope capture existed have `grantedScopes = NULL` (Facebook treats that as `ready`), and Meta grants `pages_manage_posts` only to app-role users until App Review, so a stored list can be stale either way. When the Connect tab has loaded its destinations it calls `privateRecheckPublishPermissionsAPI` (once per workspace per 10 minutes per tab, in memory, debounced, no spinner, no new strings) with the ids it shows (Threads left out):

- `publishScopeRecheckService.requestScopeRecheck({ workspaceId, destinationIds? })` (`packages/business/src/publish-destination/scope-recheck.ts`; no ids = the workspace's connected Facebook and Instagram destinations, at most 100) keeps the destinations that have a documented source, are not disconnected or `needsReconnect` and were not checked in the last 10 minutes, claims each with a Redis key (`publish-scope-recheck-claim:<workspace>:<destination>`, `SET NX`, TTL 10 minutes) and enqueues ONE `low` job `recheckPublishDestinationScopes` (generated job id, `attempts: 1`; a failed enqueue releases the claims). It returns `{ queued, fresh, failed, skipped }`: `fresh` = checked in the last 10 minutes or already claimed by another request; `failed` = could not be queued (claims released); `skipped` = unknown, not re-checkable, or beyond the 100 of one request.
- The worker job (`apps/worker/src/publish-destination/recheck-scopes.ts`, `withBlockedOwnerGuard`) re-reads the destinations one after the other, stops at the first rate-limit answer (giving back the claims it did not reach) and, when anything was written, emits `socialPostChanged` with status `scopesRechecked`; the Connect tab (`usePublishDestinationsRealtimeSync`) refetches the destinations on that status and on `failed` (a target failing is how a rejected token, a missing permission or a publishing pause is recorded), and ignores every other status.
- The write (`publishDestinationRepository.recordRecheckedScopes`) is fenced twice: the inbox token must still be the one the read used (`inboxTokenMatches` on the sha256 fingerprint), and `checkedAt` must be what it was before the platform call, so a reconnect (which stamps `checkedAt` and replaces the token), a publish refusal or another re-check that happened meanwhile wins over an older read.
- `publishStatus = 'permissionMissing'` recorded by a real publish refusal is NOT cleared by a re-check, except when it was recorded for this very token (`statusTokenFingerprint` equals the fingerprint of the token just read) and the platform now reports every required permission; then it returns to `ok`. Any other case keeps the status and its missing list; only a reconnect clears it, as before.
- A token `debug_token` reports `is_valid: false` is only logged: the existing token-health paths own `needsReconnect`. A rate-limit answer, a failure, or an answer without `scopes` leaves the stored permissions untouched.
- Public API: `POST /v1/posts/destinations/recheck-permissions` (scope `posts`, router `publishDestinations`, procedure `recheckPermissions`; CLI `post-destinations recheck-permissions`; hidden from the MCP default tool list), body `{ ids?: string[] (at most 100) }`, answer `{ queued, fresh, failed, skipped }`; the session twin is `privateRecheckPublishPermissionsAPI` behind the `broadcast` page permission. It writes stored permissions, so it is a mutation: refused on a trial-expired workspace like the other destination mutations (it is not on the read-only POST allow-lists) and the Connect tab does not call it for a read-only workspace.

**Reconnect fan-out.** One Facebook login usually owns many Pages, so reconnecting one Page refreshes the others (`reconnectFanOutService`, `packages/business/src/publish-destination/reconnect-fan-out.ts`; called by the Messenger and Instagram-via-Facebook reconnect callbacks through `runReconnectFanOut`). After the selected row commits, it takes the pages the login lists and finds, in the **same workspace**, every `IntegrationMessenger` row and every `IntegrationInstagram` row with `type = 'facebook'` whose `pageId` is among them, whose inbox is connected, whose stored authorizer `userInfo.userId` equals the reconnecting Facebook user id **and** whose app `clientId` equals the credential's. A row with no trustworthy authorizer id is skipped, and the selected row is excluded. Each row refreshes in its own transaction (long-lived token exchange, then, inside the write transaction, a row lock that re-checks the inbox is still connected and the stored app and authorizer are unchanged (the stored token is not compared: the `authorizedAt` fence below decides, so a newer fan-out still replaces what an older one wrote meanwhile); a row that was disconnected or reconnected meanwhile is skipped, never revived or overwritten; `connectionStateService.commitReconnect`, which clears `tokenRefreshError`, then a best-effort webhook subscribe and a binding reset); a failure on one row never stops the others, and nothing creates an inbox. Every row write is also fenced on the reconnect's `authorizedAt` (required; the builder handlers capture it when the reconnect starts, and it travels in every continuation job): a row whose `updatedAt` is later was written by a newer authorization and is skipped, and a row the fan-out writes is stamped with `updatedAt = authorizedAt` (not now; an explicit value in `.set()` wins over drizzle's `$onUpdate`), so two overlapping reconnects order by their start whichever job runs last, and a delayed job never restores an older token or `permissionMissing` snapshot. Known limit: other writers stamp `updatedAt` with the transaction start time, so an unrelated settings save whose transaction began before both reconnects and commits after the newer one can move the fence back and let the older delayed job write its (still valid) token and scopes; reconnecting once fixes it, and a dedicated authorization-generation column would close it. The inline run is capped at 100 pages / 20 s. The remainder goes to the `low` job `reconnectPublishFanOut` (at most 10 hops, each hop continuing the same guarded work; the page tokens travel in the payload encrypted with an AAD bound to the workspace and the Facebook user, never in plaintext). It is best effort and never fails the reconnect that already succeeded; it is skipped when the authorizing Facebook user id is unknown.

### Token upkeep

Meta tokens belong to the inbox integrations and are kept by their existing refresh paths; publishing adds none. The minute cron `refreshSocialAccountTokens` (offset 42 s, distributed lock, `withBlockedOwnerGuard` per workspace) now serves **TikTok only**: see "TikTok publishing" for its lead time, lease and rotating refresh token. A TikTok token already expired does not end the account: only a rejected refresh sets `needsReauth`. A stored token whose value cannot be parsed (unparsable payload, not a token envelope, or malformed encrypted blob: `MalformedEncryptedDataError` from `@chatbotx.io/encryption`) is permanent: `SocialTokenUnreadableError`, fenced `needsReauth`. A Web Crypto `OperationError` is also what a wrong key with a matching key id produces, so it is transient (`SocialTokenDecryptionError`): the worker logs `{ err, accountId }` and defers the account by the lease (`deferRefreshUnderLease`) without changing its status, so a bad key deployment never flags accounts for reconnect.

### API

Public (scope `posts`):

- Router `publishDestinations`: `GET /v1/posts/destinations` (grouped by network; filters `providers[]` and `states[]`; each destination has `id`, `provider`, `inboxId` or `socialAccountId`, `name`, `avatar`, `externalId`, `viaFacebook`, `state`, `missingScopes`, `contentTypes`, `pausedUntil`, `pauseReason` (publishing pause, see "Publishing pace and platform limits"); disconnected inboxes only when `states` includes `inboxDisconnected`; reading creates missing bindings, bounded and idempotent), `GET /v1/posts/destinations/{id}`, `GET|PUT /v1/posts/destinations/{id}/posting-schedule` (procedures `getPostingSlots` / `updatePostingSlots`), `GET /v1/posts/destinations/{id}/free-slots` and `GET /v1/posts/destinations/{id}/publishing-settings` (TikTok).
- Router `socialAccounts`, **TikTok only**: `GET /v1/social-accounts`, `GET /v1/social-accounts/{id}`, `POST /v1/social-accounts/{id}/verify`, `POST /v1/social-accounts/{id}/sync-destinations`.
- Posts: a target takes **exactly one** of `destinationId` or `inboxId` (an `inboxId` creates the binding when missing, in `validate` and `preview` too, so a dry run answers the same as the create it checks; the binding is an idempotent row derived from the inbox, the same one `GET /v1/posts/destinations` creates, so these dry runs stay open to `read_only` tokens); the post list filters by `destinationIds[]` and `inboxIds[]` (the old `socialAccountIds` is gone, and list queries now reject unknown parameters with 400).

CLI: `post-destinations list | get | posting-schedule get | posting-schedule update | free-slots list | publishing-settings get`, and `social-accounts list | get | verify | sync-destinations | disconnect` (`DELETE /v1/social-accounts/{id}`, scope `posts`: invariant 23 keeps the post-connect disconnect on the API; the session twin is limited to a workspace super admin, and a workspace token has a scope but no role, so the scope stands in for it). Connect and reconnect are not public on purpose. A reconnect is an OAuth redirect, so an agent reads `state` and the missing permissions from the list and tells a person to reconnect from the Posts page. `verify` and `sync-destinations` answer 409 `socialAccountNeedsReauth` (the platform rejected the token; the account is now `needsReauth`), 409 `socialAccountDisconnected`, 502 `providerUnavailable` or 422 `providerNotSupported`.

- **Instagram publishing with a Page token on `graph.facebook.com`** is not verified against a real account.

## Destination pictures

An inbox destination's picture follows the contact avatar pattern. Once a copy is stored the DTO `avatar` is its public URL. Until then it is `/media/destination-avatar/<signed token>` (a `destinationAvatar` media token naming the destination and workspace, same TTL and rate limits as `/media/avatar`; a public route). That route redirects (302) to the stored copy, or, when none exists, resolves a fresh picture URL live from Meta with the destination's token (server side only, never in a response) and redirects to it at once, then enqueues the `refreshPublishDestinationAvatar` low job (job id per destination, so repeated views collapse) to re-host and store it. A page with no picture (a Facebook silhouette) or a recent failure records `avatarFetchedAt` (no picture: now; failure: back-dated so it is retried after a day), and the route then serves the placeholder without calling Meta; the DTO returns `null` for such a row until the record goes stale (a week). Connect and reconnect still enqueue the job; the list no longer does. The UI falls back to the network icon when the image fails to load.

## Connect tab

The Posts page's **Connect** tab (`/space/<id>/posts/connect`; `/posts/accounts` redirects to it, keeping the query) lists the workspace's **connected inboxes** of Facebook, Instagram and Threads, grouped by network, so the person sees at a glance which pages can publish. A network with no inbox is hidden. It reads the same destinations as the pickers (`GET /v1/posts/destinations`).

- **One state, at most one action per row.** A row shows the avatar, the name (a small "via Facebook" tag for an Instagram inbox connected through Facebook Login) and one state chip: `ready` (green check, no button); `needsReconnect` (red, "Connection expired", button "Reconnect {name}"); `permissionMissing` (amber lock, "Publishing permission not granted", button "Reconnect to allow publishing"). The button runs that inbox's reconnect action with `returnTo: "postsConnect"`; it is gated like the channel settings reconnect, so a member who cannot reconnect channels sees the state only. A hint says "Reconnecting one Page updates every Page of the same Facebook login." (the fan-out above).
- **Name and avatar open the page on its network** (new tab, `rel="noopener noreferrer"`, an external-link icon on hover/focus, label "Open {name} on {network}"). The URL is `profileUrl` on the publish destination (public API too), built by `buildPublishDestinationProfileUrl` (`packages/utils`): Facebook from the numeric page id, Instagram/Threads from `IntegrationInstagram.username` / `IntegrationThreads.username`, TikTok from the destination's `username`; `null` (plain-text name) when missing or not a plain handle.
- **Not ready is shown, not selectable.** A destination that is not `ready` appears in the pickers but cannot be chosen; the invalidator after a reconnect refreshes every picker.
- **TikTok** is a separate compact card of publishing accounts (super admin only; the Connect button is disabled with the "coming soon" tooltip until the owner configured the publishing app). TikTok inboxes are not listed here: the publishing open id differs from the inbox open id.
- States: loading skeleton, error with retry, read-only (trial expired: every button disabled), per-network empty state hidden.
- The "Reconnect the channel" link of the Posts tab's sync-failure notice points to this tab.

## Composed posts

A **composed post** is written in ChatbotX for one or more publishing destinations (see "Publishing destinations"). It is not `ChannelPost` (a post that already exists on an inbox channel): once a later stage publishes it, a target links to the matching `ChannelPost` when exactly one inbox matches. Drafts can be published now (see "Publishing now") or scheduled (see "Scheduling").

### Statuses

- Post: `draft`, `scheduled`, `publishing`, `published`, `partiallyPublished`, `failed`, `cancelled`. Only `draft` and `scheduled` posts can be edited, and only while every target is still `pending`; a `draft` is deleted, a `scheduled` post is cancelled by the same `DELETE` (see "Scheduling"); anything else answers 409 `socialPostNotDeletable`.
- Target: `pending`, `publishing`, `processing`, `published`, `failed`, `cancelled`, `needsReview`.
- A draft's targets are `pending` with `scheduleMode: "custom"` and no `nextAttemptAt`; publishing makes them due.
- **Planned time of a draft.** A draft may remember the time picked in "Publish at" so the calendar shows it on its day: `plannedAt` (create, update; `null` forgets it) writes the targets' `scheduledAt` and timezone and **never** `nextAttemptAt` (`socialPostSchedulingRepository.setPlannedTime`, run inside the save transaction by `socialPostScheduleService.prepareDraftTime`). The publish scan (`claimDue`), `claim` and the missed-schedule sweep (`listMissed` / `failMissed`) all read `nextAttemptAt` of `pending` targets, so a draft can never publish; the post stays `draft`. Only clockless targets are touched, so a scheduled target never changes; no lead-time window applies. `plannedAt` cannot be combined with `publish`, `scheduledAt`, `queue` or `recurrence`. Scheduling the draft later (`scheduledAt`, `reschedule`) writes both columns as usual. Guarded by `packages/database/__tests__/integration/social-post-buckets.test.ts`.

### Buckets and counts

The Posts list filters and counts by a **bucket** (`socialPostBuckets`, `@chatbotx.io/utils/social-post`). A post is in exactly one, the first that fits: `needsAttention` (post `failed` or `partiallyPublished`, or any target `failed` / `needsReview`), then `drafts` (`draft`), `scheduled` (`scheduled` or `publishing`), `published` (`published`). A `cancelled` post is in none and only counts under `all`. One SQL predicate (`bucketCondition`, `packages/database/src/repositories/social-post/buckets.ts`) backs both the list's `bucket` filter and the counts, so a count opens exactly the posts it counted. `GET /v1/posts/counts` (`socialPosts.counts`, CLI `social-posts counts`; session twin `privateCountSocialPostsAPI`) returns `{all, drafts, scheduled, published, needsAttention}` for the workspace in one grouped statement (`FILTER` aggregates, workspace predicate), optionally narrowed by `providers[]`, `destinationIds[]`, `inboxIds[]`. The static path is registered before `/v1/posts/{id}`.

### Create, idempotency and media

- `POST /v1/posts` writes the post and every child row in one transaction. Destinations and topics must belong to the workspace; a content type that the destination's network does not publish is refused even for a draft. Content rules (text length, file formats) are reported by `validate` and enforced when a post is scheduled, so a draft can be incomplete.
- `idempotencyKey` (body, up to 200 characters) makes a create safe to repeat. The request is normalised (text and link trimmed, topic ids sorted and de-duplicated) and hashed with SHA-256 (Web Crypto, so the module stays Edge-safe). The partial unique index `(workspaceId, idempotencyKey) WHERE idempotencyKey IS NOT NULL` decides the winner of two concurrent creates; the loser returns the winner's post when the hash matches and answers 409 `socialPostKeyConflict` when it does not. This is separate from the public API's `Idempotency-Key` header, which also applies to the POST.
- A file is a Media Library file id (checked to be the workspace's own) or a public URL. A URL is imported by a Node-only importer registered by the builder's route handlers (a process without one refuses URL imports). Every request, redirect hops included, is vetted by the SSRF guard and its socket connects only to the addresses the guard returned for that exact URL (TLS name and `Host` keep the URL's host), so a name that resolves differently at connect time (DNS rebinding) cannot reach an internal address. Limits per request: 50 MB per file, 100 MB for all files together, one 60 s deadline for all of them; only JPEG, PNG, GIF, WebP and the video types the publishing rules know are kept (SVG and everything else is refused). Destinations, content types and topics are checked, and an update's post is checked to exist and be editable, before anything is imported. Files a call imported are removed (object and library row) when the call fails, rolls back or loses an idempotency race; a cleanup failure is logged, never thrown. Downloads happen before the transaction opens.
- Video duration and image dimensions are not probed (`durationMs` is `null`): duration limits are enforced only when a duration is known.

### Publishing rules (registry)

`packages/utils/src/post-publishing.ts` is the single source for what each network accepts: per network and content type the text limit, the file count, accepted formats, size and duration, whether a link is allowed, the settings (`optionsSchema` and the UI field descriptors) and the network's daily post limit. It is pure (no Node imports). The content types each network offers (the `contentTypes` of a social account and of a destination in the API) are `enabledContentTypes()` of this registry, not a second list. `normalisePublishTarget` is the one function behind `validate`, `preview` and (later) the publisher. Issues are `{targetIndex, destinationId, field, code, message}` with finite codes, so the UI can translate them.

**Links in the caption.** Only the Facebook `link` type has a structured link field. For every other content type that carries text, `normalisePublishTarget` builds the text with `captionWithLink` (`packages/utils/src/post-publishing-validate.ts`): the link is appended after a blank line (`\n\n`) unless the caption already contains that exact URL, and `normalised.linkUrl` becomes `null` (the publisher sends no separate link). `textTooLong` measures that final text, and `textRequired` is satisfied by a link alone. `validate`, `preview` (its `text`, `charactersUsed`) and the publisher call the same function, so the preview is what is published. The composer shows a muted note ("The link will be added to the end of the caption.") on those cards, never on a Facebook `link` card. `linkNotSupported` is now raised only for a type that carries no text at all (a story).

### Publishing now

`publish: "now"` on create or update, or `POST /v1/posts/{id}/publish`, publishes every destination at once. Every path calls `socialPostPublishService.publishNow`; there is no migration beyond the Stage 8 columns and scanner indexes.

**Flow.** The post is first checked as stored (`normalisePublishTarget` per target plus the destination blockers): any issue refuses the whole post with 422 `socialPostContentInvalid` and every issue in `data.issues` (create with `publish: "now"` validates before saving, so no draft is left behind). Then, in one transaction under the post row lock (the check is repeated there, so an edit that committed first is seen), the pending targets get `nextAttemptAt = scheduledAt = now` and the post becomes `publishing` (a post that is not `draft`/`scheduled` answers 409 `socialPostNotPublishable`, so a repeat enqueues nothing; a repeated idempotent create of a post already publishing returns it). After the commit one job per target is enqueued on queue `postPublish` (jobId `social-post-target-<id>`, removed when it ends, no BullMQ retries). A failed enqueue is logged only: the minute cron `enqueueSocialPostTargets` claims due targets (`UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED LIMIT 100)`, pushing `nextAttemptAt` 5 minutes ahead; distributed lock) and enqueues them again. A job claims its target only while `nextAttemptAt <= now + 5 minutes` (the scan's push-back), so a job queued before the user rescheduled the target to a later time than that refuses to claim it; a reschedule to within those 5 minutes after the scan queued the job may still publish at the earlier time.

**Job (`apps/worker/src/post-publish`, behind `withBlockedOwnerGuard`: a blocked owner is a bare return, the target stays pending).**
1. Claim: conditional UPDATE `pending` to `publishing` with `leaseExpiresAt = now + 10 min`, `attemptCount + 1`, `publishStartedAt = NULL`. No row means another worker has it.
2. Pre-flight: publisher registered (by `PublisherKey`), then `loadPublishCredentials` (see "Credentials at publish time"; the token is read per call and never logged or returned). Failures here end the target `failed` with a code (`publisherUnavailable`, `inboxDisconnected`, `inboxNeedsReconnect`, `publishPermissionMissing`; TikTok: `accountNeedsReauth`, `accountDisconnected`, `destinationInactive`, `accountNotConnected`). The content is re-validated against the registry (`payloadInvalid` with the issue code).
3. Marker: guarded UPDATE `publishStartedAt = now` (status `publishing` and the claim's lease). Only then the publisher is called. No HTTP call runs inside a transaction.
4. Result, one UPDATE that presents the lease (a worker that lost its claim changes nothing): `published` (id, permalink, `publishedAt`), `pending` (`processing`: the container id is stored in `continuation` and `leaseExpiresAt` is the next read time), or `failed`.

**Failure classification** (`classifyFailure`): a rate-limit or restriction answer (`rateLimited`, `accountRestricted`) has its own budget and waits 1 h, 2 h, 4 h (+ up to 5 min of jitter, or the network's own reset hint when longer, capped at 24 h) without spending an attempt (`SocialPostTarget.rateLimitAttempts`), then fails with `errorCode = publishRateLimitExhausted`; see "Publishing pace and platform limits". Every other retry needs the error to prove nothing was created (`provablyNotCreated`) and the category to be `networkError`, `quotaExceeded` or `unknown`: waits 1, 5, 15, 60 minutes, at most 5 attempts, then `failed`. `payloadInvalid`, `mediaInvalid`, `notFound`, `authFailed`, `permissionDenied` fail at once; `authFailed` and `permissionDenied` also record the state through `recordPublishAuthFailure` (see "Credentials at publish time": an inbox token gets `tokenRefreshError = 'publishTokenRejected'` or the binding `permissionMissing`, never `Connection.status`; a TikTok account becomes `needsReauth`). A failure that may have created the post (`provablyNotCreated: false`, not a limit answer) goes to `needsReview` and is never retried automatically, **unless the publish has no provider-side identity** (the target holds no `continuation`: a direct Facebook text, link, photo, multi-photo or photo-story publish, a Facebook feed video whose `POST /{page}/videos` never returned its id, a TikTok `init` that never returned its `publish_id`): the post cannot be read back or recognised later, so a `networkError` or `unknown` answer is then retried on the same ladder (`retryUnknownOutcome`) and the Page may receive the post twice. That is a deliberate choice: such a publish is never guessed or adopted. A failure after a continuation exists (an Instagram or Threads container's final call, a TikTok `publishId`, a Facebook video or reel after `finish`) keeps `needsReview`. A crash in the job after the marker is the same: `internalError` retries when there is no continuation and ends in `needsReview` otherwise; before the marker it retries.

**Recovery (`recoverSocialPostTargets`, minute cron).** The cron only claims: it takes targets (and parts) with an expired lease (index `SocialPostTarget_lease_idx`), gives each a new 10 minute lease and adds one `checkTarget` / `checkPart` job per claim to the `postPublish` queue (job id `social-post-check-target-<id>-<leaseMs>`, so a re-claim has a new id), then runs the quota sweep. The job (behind `withBlockedOwnerGuard`, like publishing) re-reads the row only while its lease is still the stored one (`findExpiredClaim`; otherwise it does nothing) and then does the recovery below, so a slow network (a TikTok chunk upload takes up to 4 minutes) holds one worker slot instead of the whole tick, and finished Instagram/Threads containers are not starved. If a job cannot be queued, nothing is lost: the lease expires and the next tick claims the target again. The recovery of one claim: no marker means the attempt never reached the network, so it goes back to `pending` (or `failed` `attemptsExhausted` after 5); a marker with no `continuation` is an unknown-outcome direct publish: it goes back to `pending` on the retry ladder (1, 5, 15, 60 minutes; the attempt is spent; error `outcomeUnknownRetried` is recorded) and after the fifth attempt becomes `failed` (`attemptsExhausted`), never `needsReview`, and the destination may get the post twice; a `continuation` (Instagram/Threads container id) is read again with the publisher's `checkStatus`, whose container id is the provider-side identity (Instagram and Threads publish in `checkStatus` when the container is `FINISHED`; the final publish call is never replayed once its `finalCallAt` marker is stored, and a failure of that call that may have created the post, or `container_already_published`, is `needsReview`). An Instagram or Threads container not finished two hours after its marker fails (`processingTimeout`; nothing was published, as only the final publish call posts it). A target whose continuation can publish on its own (a TikTok `publishId`, a Facebook feed video, a reel or video story after `finish`) goes to `needsReview` instead, with the same code and "may already be published; check the page": a manual retry of a failed one would start a second upload. The same rule applies when recovery finds the destination gone, the credentials rejected or no publisher registered. **Final-call marker.** The calls that create the post run inside `checkStatus` (Instagram and Threads publish, Facebook reel and video story `finish`). Right before one, the publisher calls `request.checkpoint`, which recovery implements by storing the continuation plus `finalCallAt` (epoch ms) with `processing` and a new lease (the lease fence moves with it); if that write is lost, the call is not sent. A continuation holding `finalCallAt` is never sent that call again: `checkStatus` answers `final_call_unconfirmed` (not provably uncreated, so `needsReview`), and every non-reread recovery path (timeout, destination gone, credentials rejected, no publisher) settles `needsReview` instead of `failed`. Only a call answered "media not ready" returns to polling with the marker cleared. A video story never stores `finishing` (it publishes in the finish call), so the marker is its only trace; a reel stores `finishing` after finish. Follow-up parts (replies) use the same checkpoint (their lease is 10 minutes), and a marked part is never failed by recovery: it goes to `needsReview`. Retrying a `needsReview` target, in the composer (after a confirmation), through `POST /v1/posts/{id}/targets/{targetId}/retry` or the CLI, publishes again and may post twice; the procedure description says so. Check the page first, or mark it published. Facebook text, link, photo, multi-photo and photo-story posts have no container: `checkStatus` is not called for them. A Facebook feed video, reel or video story keeps its video id in `continuation` (see "Rich media"). **Unknown outcome of a direct Facebook publish.** A direct Facebook text, link, photo, multi-photo, photo-story or single-call feed-video publish whose answer never arrived (timeout, lost response, worker crash after the marker) is **retried automatically and may post twice**: the publisher does not look the post up on the Page and nothing is adopted, because without a provider-side identity any match would be a guess. The retry ladder and the five-attempt limit above apply. The marker write (`markAttemptStarted`) is still fenced on the destination's pace reservation (`EXISTS` on `PublishDestination.lastPublishStartedAt = reservedAt`; it returns `marked` | `leaseLost` | `reservationTaken`), so an older attempt that stalled after reserving and wakes up after a newer attempt reserved can never reach the network: `reservationTaken` sends nothing and `runTarget` gives the claim back like a spacing deferral (`releaseClaim`, no attempt spent).

**Post status** is recomputed under the post row lock in the same transaction as every target result (`computePostStatus`): any `publishing`/`processing`/`needsReview` target keeps the post `publishing`; a post that is not published keeps its state while targets are only `pending`; when every target is final: all published is `published`, some is `partiallyPublished`, none is `failed` (all cancelled is `cancelled`); `completedAt` is set then.

**Review actions.** `POST /v1/posts/{id}/targets/{targetId}/retry` (target `failed` or `needsReview`: back to `pending`, due now, attempt count reset, error and continuation cleared; 409 `socialPostTargetNotRetryable` otherwise) and `.../resolve` with `{outcome: "published" | "retry"}` (only for `needsReview`: `published` marks it published with no id; `retry` is the retry; 409 `socialPostTargetNotReviewable` otherwise).

**Link to the inbox.** After a target is stored `published`, a Facebook, Instagram or Threads destination already knows its inbox (`PublishDestination.inboxId`); TikTok is resolved by `openId`. Exactly one match upserts the `ChannelPost` (`insertBare`, or the row the sync already has), sets `channelPostId` and copies the post's topics; no match or several leave it null. Best effort: a failure is logged and never undoes the published result.

**Trial expired (invariant 14).** `publish`, `retry`, `resolve`, and create/update with `publish: "now"` answer 403 `trialExpired` (or `macLimitReached`) from the trial gate (a handler that checks the owner itself answers 402 `workspaceBlocked`); the publish job and the recovery scan do not publish or recover a blocked workspace's targets while it is blocked. What happens to a due target that waits that long is set by the late-publish rule (see Late publish under Scheduling): after 6 hours it fails as `missedSchedule`. Publishing consumes the message quota (see Message quota below).

**Message quota.** Publishing consumes the account's message quota (`messageUsageService`, the same owner pool and counters a chat send uses, invariant 12): 1 message per destination that ends `published`, a follow-up thread or first comment included in that 1. Drafts, scheduling, queueing, rescheduling, recurrence copies and feed drafts are free, and so are `failed` and `needsReview` targets and a head that is out while its parts are still publishing; the charge comes when the target settles `published` (live, by recovery, or by a person confirming it). The three `published` writes (`settle`, `finishFromPart`, `resolveAsPublished`) set `SocialPostTarget.quotaChargePending` in the same UPDATE; after the commit the service claims it with a conditional UPDATE (`quotaChargedAt` is set, only the winner charges), then charges 1 and, if the charge throws (only when nothing was counted: the workspace could not be read), gives the claim back. The recovery cron sweeps targets still pending (partial index, bounded batch, oldest first), so such a charge is retried. A counter that fails after another was written is logged and not repeated, so a retry never counts twice. A replayed settle or redelivered job never charges twice; a crash between the claim and the charge, or a database error during it, can lose that one charge. At the limit the publish job fails the target before the first call: `errorCategory = quotaExceeded`, `errorCode = postMessageQuotaExceeded`, no provider call, no attempt spent; a person retries it after a top-up or the next billing period (parts are gated the same way before each part starts). Publish now, create or update with `publish: "now"`, and retry answer 429 `postMessageQuotaExceeded` beforehand as an advisory check (after the 402 trial gate); only the worker gate is authoritative. A workspace without a resolvable owner is not charged and a plan without a limit never blocks.

**Operations.** Queue `postPublish` runs in the `low` worker process (concurrency 3, `apps/worker/src/low/worker.ts`; per-network job slots on top of it, see "Publishing pace and platform limits"). The crons run at second offsets 46 and 50 of every minute. Registry of publishers: `apps/worker/src/post-publish/publishers.ts`, keyed by `PublisherKey` (`facebook`, `instagram`, `instagramFacebook`, `threads`; the two Instagram keys share one publishing core over two transports;  `tiktok`, the video publisher of "TikTok publishing"; TikTok photos stay disabled and are refused at validation with `contentTypeDisabled`).

### TikTok publishing

Posts a **video** to a connected TikTok account through the Content Posting API (Direct Post). It is the only network still published through a separately connected social account, with its own TikTok app (Login Kit + Content Posting API at `open.tiktokapis.com`); the inbox TikTok integration (Business Messaging API, `tiktok` credential, its scopes and tokens) is untouched.

**Setup (owner).**

1. Create an app at developers.tiktok.com and add the products **Login Kit** and **Content Posting API** (enable *Direct Post*). Request the scopes `user.info.basic` and `video.publish` (`video.upload`, the draft scope, is not used).
2. Register the redirect URI shown on the Platform credentials card "TikTok publishing" (`<origin>/integrations/tiktok/callback`, the same path as the inbox app but registered in this other app).
3. Save the app's client key and secret in Platform credentials, card **TikTok publishing** (credential type `tiktokPublishing`, stored encrypted like the other apps; admin and reseller scope, a workspace inherits its owner's). Until this exists the Connect button stays disabled.
4. **Audit.** Until TikTok audits the app, every post is forced to `SELF_ONLY`, at most 5 users may post in 24 hours and the posting account must be private (`unaudited_client_can_only_post_to_private_accounts`, `reached_active_user_cap`). TikTok's guidelines say the API is meant for creators posting their own content to a wide audience, not a tool for accounts a team manages; whether a multi-account scheduler passes the audit is the owner's call to make with TikTok.
5. Photo posts need `PULL_FROM_URL`, which needs the media URL prefix (our storage/CDN domain) verified as owned by the app in the TikTok developer portal (`url_ownership_unverified` otherwise). Videos use `FILE_UPLOAD` and need no verification.

**Connect.** The same `socialAccount` OAuth flow (nonce, super admin) with `client_key`, scopes comma separated, `https://www.tiktok.com/v2/auth/authorize/`; the code is exchanged at `POST /v2/oauth/token/` (form encoded). The identity is `GET /v2/user/info/?fields=open_id,avatar_url,display_name` (`user.info.basic`; the `@username` needs `user.info.profile`, not requested, so `username` is empty). `grantedScopes` comes from the token response `scope`, so a withheld permission is reported by name. One `profile` destination keyed by `open_id`.

**Tokens.** The access token is short lived, so the minute cron claims TikTok accounts whose token expires within 30 minutes (other networks keep the 14 day lead) and refreshes with the refresh token. TikTok **rotates** the refresh token: the new one replaces the old one in the same `UPDATE` that stores the new access token, under the existing lease + read-token fence (one refresh per account at a time). An access token already expired does not end the account: only a rejected refresh (`invalid_grant`, a revoked/expired refresh token) sets `needsReauth` / `refreshRejected`. This also holds when a call (Verify, publishing settings, a publish) meets `access_token_invalid` before the cron has renewed the token: `socialAccountService.rejectAccessToken` leaves a connected account whose stored expiry has passed and that holds a refresh token untouched (the scan claims expired tokens), and the call answers 502 `providerUnavailable`; a rejection with a still-valid expiry (revoked), no refresh token or an unknown expiry sets `needsReauth` / `tokenRejected` at once. If the claim is lost after TikTok already rotated, the new refresh token is lost and the next refresh is rejected (account needs a reconnect); the window is one HTTP round trip. Disconnect revokes the token (`POST /v2/oauth/revoke/`, best effort, reading the credentials included: an unreadable token only skips the revoke) before wiping it.

**Registry (video).** MP4 / MOV / WebM, up to 4 GB, up to 10 minutes (the creator's own limit comes from creator info at publish time and fails `duration_check_failed`), caption up to 2,200 UTF-16 units, one file, no link. Settings: `privacyLevel` (required, no default, one of `PUBLIC_TO_EVERYONE | MUTUAL_FOLLOW_FRIENDS | FOLLOWER_OF_CREATOR | SELF_ONLY`), `allowComment`, `allowDuet`, `allowStitch` (all off by default), `commercialContent` with `brandOrganic` ("Your brand" = Promotional content) and `brandContent` ("Branded content" = Paid partnership; at least one when `commercialContent` is on; cannot be `SELF_ONLY`), `isAigc`, `coverTimestampMs`. The image type is disabled (reason above). The daily post limit is not enforced: TikTok says "typically around 15" per creator and shared across apps.

**Creator info.** `GET /v1/posts/destinations/{id}/publishing-settings` (scope `posts`, router `publishDestinations`; CLI `post-destinations publishing-settings get`) reads `POST /v2/post/publish/creator_info/query/` live: nickname, `privacyLevelOptions`, comment/duet/stitch disabled, `maxVideoPostDurationSec`, `canPostNow` (false with `cannotPostReason` when TikTok answers `spam_risk_too_many_posts`, `reached_active_user_cap`, ...). TikTok allows 20 reads a minute per token: the result is cached 30 seconds in Redis per account (dropped on disconnect and re-auth), and a `rate_limit_exceeded` answer is remembered 30 seconds as a throttle so every validation in that window answers "unavailable" (502 `providerUnavailable`, no issue) without calling TikTok again. Any other outage is not cached. The logic lives in `packages/business` (`socialAccountOperationService`, `creatorSettingsIssues`, subpaths `social-account/operations` and `social-post/creator-settings`); the builder procedures are thin calls. `validate`, `preview` and `create` reject a `privacyLevel` outside `privacyLevelOptions` with an `optionsInvalid` issue naming `privacyLevel`; the publisher checks again right before the post and fails `privacy_level_option_mismatch` without creating anything.

**Composer request.** `buildContent` always sends each target's `options` (TikTok's privacy and disclosure settings do not depend on "Customise for this channel") and its `contentType` when one is pinned. `stateFromPost` pins the stored type only when the files and link would not infer it again (`inferContentType`, shared in `packages/utils/src/post-publishing-validate.ts`), such as a Story or a Facebook Reel, and shows that target as customised; a type the server infers stays unpinned so adding a file can still change it.

**Composer.** The TikTok target card shows the creator nickname, the privacy select (no default, only the creator's options), Comment / Duet / Stitch checkboxes (off; disabled when the creator disabled them), the commercial content toggle (off) with the two required labels and TikTok's label text, the branded-content-not-private rule, the AI-generated switch, the consent line linking to TikTok's Music Usage Confirmation (plus Branded Content Policy when branded), and the processing notice. Strings: `composer.tiktok*`, `composer.options.*`.

**Publishing flow.** `publish`: creator info (must be able to post, privacy level one of its options, duration within its limit) then `POST /v2/post/publish/video/init/` with `FILE_UPLOAD` (`video_size`, `chunk_size`, `total_chunk_count`: files up to 20 MB go whole, larger ones in 20 MB chunks, the last absorbing the remainder, as the transfer guide requires 5-64 MB chunks). TikTok documents no idempotency key, so `publish_id` is returned as `pending` with the upload plan in `continuation` **before any byte is sent**; a target is never initialised twice once it has its `publish_id`; an `init` whose answer never arrived left no identity and is retried like any unknown outcome without one (TikTok may then hold a second, never-uploaded publish). `checkStatus`, phase `upload`: each chunk is read from the media URL with a `Range` request (at most one chunk in memory) and `PUT` to the `upload_url` (valid one hour) with `Content-Range`, within a 4 minute budget per call (the offset is stored; before sending, the call reads the publish status and resumes from its `uploaded_bytes` when that is a planned chunk boundary, moves to processing when every byte is uploaded, and keeps the stored offset otherwise, so a chunk TikTok already accepted is not sent twice after a crash); a network error during the upload is a failure that is not provably "nothing created", so the target goes to `needsReview` (TikTok may still publish). The upload is complete only when TikTok answers `201 Created`; if every planned chunk was sent and the last answer was `206 Partial Content`, the call fails with `upload_not_confirmed` (also not provably uncreated, so `needsReview`) instead of moving on to status polling. Phase `processing`: `POST /v2/post/publish/status/fetch/` (30 per minute per token): `PROCESSING_UPLOAD | PROCESSING_DOWNLOAD | SEND_TO_USER_INBOX` keep polling, `PUBLISH_COMPLETE` publishes, `FAILED` is classified by `fail_reason` (`file_format_check_failed`, `duration_check_failed`, `frame_rate_check_failed`, `picture_size_check_failed`, `video_pull_failed` → `mediaInvalid`; `internal` → retryable; `spam_risk*`, `auth_removed`). TikTok returns the post id (`publicaly_available_post_id`, TikTok's spelling, parsed as strings) only for a public, moderated post, which can take hours; a private (`SELF_ONLY`) or not yet moderated post has none, so the target stores the `publish_id` as its external id and no permalink. Errors map: `access_token_invalid` → `authFailed` (account `needsReauth`), `scope_not_authorized` → `permissionDenied`, `spam_risk_too_many_posts` / `spam_risk_too_many_pending_share` → `rateLimited` at account level, `rate_limit_exceeded` → `rateLimited` at `token` scope (a per-minute throttle per access token: init 6, status 30, creator info 20; retried after about 60 s or the reset hint, with no count toward pausing the destination and none against the 1/2/4 h ladder, still bounded by the 5 attempts). A throttle on the status read of a post that already has a `publish_id` never starts a second init: the continuation (and the `publish_id`) is kept and the read repeats after at least 60 s, counted in `statusThrottles`; the tenth throttle in a row fails the target with `status_throttle_exhausted` (not provably uncreated, so it goes to `needsReview`). Any other status-read failure is also reported as not provably uncreated, `spam_risk_user_banned_from_posting` → `payloadInvalid` (fails for good, no retry), `reached_active_user_cap` → `quotaExceeded`, `url_ownership_unverified`, `privacy_level_option_mismatch`, `invalid_param` → `payloadInvalid`. Delete is refused (`delete_not_supported`): the API has none (`canRemove: false`).

**UNVERIFIED / open.**

- Token lifetimes: the docs say 2 hours / 180 days but also show examples with other values; only the response fields are used. The exact `error` of a revoked or expired refresh token is assumed `invalid_grant`.
- The legal links (Music Usage Confirmation, Branded Content Policy) are TikTok's public legal pages, typed from the guidelines' wording and not opened.
- Whether the public id of a moderated post reaches the target: nothing polls after `PUBLISH_COMPLETE`, so a post that was still in moderation then keeps the `publish_id` as its id. A later poll or the `post.publish.publicly_available` webhook (not wired) would fill it.
- The upload runs inside the status poll job; a very large file relies on the job lease being longer than the 4 minute budget plus one chunk.
- The access token lives about 2 hours: a publish that races a cron outage fails `access_token_invalid`; that target still fails (an auth failure is not retried automatically), but the account stays connected when only the access token expired (see Tokens).
- The publishing app's open id differs from the inbox app's, so published posts are not linked to the inbox `ChannelPost`.
- Photo posts (disabled, setup above), drafts (`video.upload`, `inbox/video/init/`) and the status webhooks are not implemented.

### Rich media

Content types beyond text and one image. All media are read by the network from a public URL (`getPublicFileUrl`); no file bytes pass through ChatbotX. Every flow follows the duplicate-prevention rule: the marker is written before the first call that can create a post; provider-side ids are returned as `continuation` as soon as they exist; a call that may have created the post and can be tied to a provider-side id (a container, an upload, a publish id) is never retried (`needsReview`); a direct Facebook publish that leaves no such id is retried when its outcome is unknown (it may post twice).

### Removing a post

`DELETE /v1/posts/{id}?removeFromChannels=true` (session twin: `privateDeleteSocialPostAPI` with `removeFromChannels` in the body; both call `socialPostOperations.delete`) takes the published destinations down from their networks. The post and its targets stay as history. It answers 200 `{deleted: false, removal: {targets: [{targetId, status}]}}`, with `status` one of `queued` (a job was enqueued), `removed` (already gone), `unsupported` (the network or login offers no delete, e.g. Instagram Login or TikTok, so the target stays published) and `notPublished` (nothing on the network). A post with no published destination answers 409 `socialPostNotRemovable`. The plain `DELETE` (no flag) is unchanged apart from the body `{deleted: true, removal: null}` it now returns instead of 204.

- **Which networks delete.** Registry flag `canRemove`: Facebook `DELETE /{post-id}` or `DELETE /{video-id}` (<https://developers.facebook.com/docs/pages-api/posts>, <https://developers.facebook.com/docs/graph-api/reference/video/>); Threads `DELETE /{media-id}`, which needs the `threads_delete` permission and is limited to 100 per day per account (<https://developers.facebook.com/docs/threads/posts/delete-posts>); Instagram only through Facebook Login: `DELETE /{ig-media-id}` on `graph.facebook.com` with the Page token (needs `instagram_basic` + `instagram_manage_contents`; posts, stories, reels and whole carousels, never one child of a carousel; <https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-media>). **UNVERIFIED:** that page shows DELETE in its heading and curl example but `POST` in its request syntax; the publisher sends DELETE. Instagram Login (`graph.instagram.com`) documents no delete, so `publisherCanRemove('instagram')` is false: the removal request reports `unsupported` for that target at once (`socialPostRemovalRepository.listForPost` returns the destination's `publisherKey`, derived like the publish credentials, and the request checks `publisherCanRemove`); a target that still reaches the worker records `removalUnsupported`. TikTok is not offered. A delete is never retried automatically (a timed-out call may have succeeded; asking again that finds the media gone counts as removed). Instagram answers 100/33 both for a deleted media and for a missing permission, so on that answer the publisher sends one read-only `GET /{media-id}?fields=id` with the same token: also 100/33 means the media is gone (`notFound`, target becomes removed); readable keeps `permissionDenied`. Instagram Facebook-Login connections made before `instagram_manage_contents` was requested answer a permission error, recorded as `removalPermissionMissing` like Threads (the worker keys it on `threads` and `instagramFacebook`), and the row shows the translated reconnect message. The Threads connect flow now requests `threads_basic`, `threads_content_publish`, `threads_manage_replies` and `threads_delete`. A Threads connection made before that has no captured scopes (they read as unknown, so the destination shows ready), and its removal answers a permission error: the worker records it as `errorCode` `removalPermissionMissing` and the target row shows "Reconnect this account to allow deleting posts." until the account is reconnected. The 100 deletes per day limit is read live from `threads_publishing_limit` and enforced (see "Publishing pace and platform limits"). Facebook: the `pagepost` reference says "Only select developers can perform this operation using the API" for `DELETE /{page_post_id}` (<https://developers.facebook.com/docs/graph-api/reference/pagepost/>), so `canRemove: true` can still answer a permission error (code 200) for an app without that access; the error is shown as is. Facebook's video delete reference names the `publish_pages` permission, which the connect flow does not request either; the Page delete of a post needs `pages_manage_posts`.
- **State.** One nullable column, `SocialPostTarget.removedAt` (created with the table in migration `add_posts_management`); no new status. The target stays `published`. The worker sets `removedAt` and, for a linked target, `ChannelPost.removedAt` (the row stays: comments and contacts point at it). A refusal is written to the target's existing `errorCategory` / `errorCode` / `errorMessage` (a published target has them cleared otherwise); a later success clears them. A confirmed "not found" answer counts as removed: the goal is met, and it is what a repeat sees when a worker died after the network deleted the post but before `markRemoved` (there is no durable marker before the delete call, and adding one needs a migration). On the delete path only Graph code 803 is confirmed gone; Graph code 100 with subcode 33 ("object does not exist, cannot be loaded due to missing permissions, or does not support this operation") and code 21 are mapped to `permissionDenied`, so a lost permission never marks a still-public post as removed (the target stays published with the error recorded). A worker that dies between the delete and `markRemoved` otherwise leaves the target published until a repeat.
- **Where it runs.** Never inside the request or a transaction: the request only classifies targets and enqueues one job per target on queue `postPublish` (`removeTarget`, jobId `social-post-remove-<id>`, no BullMQ retry), which the `low` worker runs behind `withBlockedOwnerGuard`. Repeating the request while a job waits is dropped by the job id; after a refusal the person asks again. `emitSocialPostChanged` announces each result.
- **Trial expired.** Removal is an outward action on the network, so it is refused with 402 `workspaceBlocked` (like publishing and retrying), while deleting a draft and cancelling a schedule stay allowed (invariant 14). The job of a blocked owner is a bare return.
- **UI.** The edit page lists the destinations with "Remove from channels" (translated confirm dialog) when a target is published and not removed; a removed target shows "Removed from the network"; Instagram targets are reported in a warning toast.

### Data

### How a target with parts publishes (no duplicates)

1. The head runs the unchanged target pipeline (claim, marker, publish, container read). When the head is out and the target has parts, it settles as `headPublished`: the target stays `processing` with **no lease** (the recovery scan ignores it), `externalPostId`, `permalink` and `publishedAt` are stored, and in the same transaction the first part gets `nextAttemptAt`. After the commit one `postPublish` job `publishPart` (jobId `social-post-part-<id>`) is queued.
2. A part has its own claim: `pending` to `publishing` with a lease only while its target is `processing` and **every earlier part is `published`** (one conditional UPDATE), so two workers cannot take it and part N+1 cannot start before part N. It writes its marker before the network call, stores the Threads container id in its own `continuation`, and every write presents its lease.
3. Settling a part runs in one transaction under the lock order post row, target, parts: a published part makes the next one due (queued after the commit) or, when none is left, publishes the target and links the inbox post; a `failed` or `needsReview` part makes the target `failed` / `needsReview` (push as for a target). The target is `published` only when every part is.
4. Recovery (`recoverSocialPostTargets`, same scan) takes parts with an expired lease: a stored container is read again and a published result adopted; an attempt that never reached the network goes back to the queue (up to five attempts); one that sent the request and left no identity waits for a person (`needsReview`, never retried alone). Due retries and lost jobs are found by the due scan (`enqueueSocialPostTargets`).
5. **Retry / resolve.** `retry-target` and `resolve-target` on a target whose head is published act on the **first part that is not published** (optional `partId` must name that part, else 409 `socialPostPartNotResumable`): retry resumes there, the head is never posted again; `outcome: "published"` marks that part published and the chain continues (a part marked by a person has no id, so the next reply answers the nearest earlier part that has one, else the head). A head that is itself unconfirmed (`needsReview`, no id) and has parts cannot be marked published (409 `socialPostHeadUnconfirmed`): parts need its id; retry the destination instead.

### API

`create` and `update` targets take `parts: [{text}]` (max 10) and `firstComment: {text} | null`; an edit restates them as a whole. `validate`, `preview`, `publish` and scheduling report issues with `field` `parts[i].text`, `firstComment.text` or `parts` and `partIndex` (codes `partsNotSupported`, `firstCommentNotSupported`, `tooManyParts`, `partTextRequired`, `partTextTooLong`); a draft may store invalid parts, publishing refuses them (422). Reads return `targets[].parts[]` with the status of each part. Creating, updating and retrying are refused with 403 `trialExpired` (or `macLimitReached`) on an expired plan; reads and cancel stay open. Realtime and push reuse `emitSocialPostChanged` / `announceSettledTarget`.

### UI

The composer's destination card shows `parts-editor.tsx` only when the network's rules offer parts: add, remove and reorder parts, a counter per part in the network's unit, and the first-comment field where supported. The edit page lists each part with its status; Retry and "Mark as published" appear on the first part that needs them.

## Publishing pace and platform limits

Publishing spaces itself and slows down before a network does it for us. Every number lives in one registry, `packages/utils/src/publish-limits.ts` (`PROVIDER_PUBLISH_LIMITS`, `dailyCapFor`, `RATE_LIMIT_BACKOFF_MS`, `PUBLISH_PAUSE_MS`). **Official** means the platform's own documentation states it (URL below, checked 2026-11-24); **our default** means no platform number exists and we chose a conservative one. A default is never a platform fact; change it in the registry only.

| Rule | Facebook Page | Instagram | Threads | TikTok |
| --- | --- | --- | --- | --- |
| Minimum gap between two publish starts on one destination | 5 min (default) | 10 min (default) | 5 min (default) | 15 min (default) |
| Jitter added when a publish is pushed back | 0 to 90 s (default) | same | same | same |
| Posts per rolling 24 h | feed/photo/video 25 (default); Reels 30 (**official**) | live `content_publishing_limit.config.quota_total`; fallback 50 (**official**: the guide says 100 and the reference says 50, so the live value wins and the lower is the fallback) | live `threads_publishing_limit` quota; fallback 250 (**official**) | 15 (default; TikTok names the error `spam_risk_too_many_posts` but documents no number) |
| Concurrent publish jobs for the network, all workers | 3 (default) | 2 (default) | 2 (default) | 1 (default) |

Other official figures the code relies on: Threads replies 1000 per rolling 24 h (parts are not gated, see below); TikTok init 6 requests per minute per user token, status fetch 30 per minute, creator info 20 per minute; Graph `estimated_time_to_regain_access` is in **minutes**; `X-App-Usage` and `X-Business-Use-Case-Usage` carry no `Retry-After` (none is documented). Sources: Instagram `https://developers.facebook.com/documentation/instagram-platform/content-publishing` and `.../instagram-graph-api/reference/ig-user/content_publishing_limit.md`, error codes `.../instagram-graph-api/reference/error-codes.md`; Threads `https://developers.facebook.com/docs/threads/overview`; Graph limits `https://developers.facebook.com/docs/graph-api/overview/rate-limiting/` and `.../guides/error-handling/`; Reels `https://developers.facebook.com/docs/video-api/guides/reels-publishing`; TikTok `https://developers.tiktok.com/doc/content-posting-api-reference-direct-post` (and `-upload-video`, `-query-creator-info`, `-get-video-status`). Not found in any official page, so not used as facts: a Facebook Page posts-per-day number, a TikTok daily number, a `Retry-After` header, `X-Page-Usage`, error subcode 1390008.

**The pace gate** (`social-post/publish-pace.ts`, `checkPace`). `runTarget` claims a target, loads credentials and builds the request, and then asks the gate BEFORE the attempt marker and before any network call. A deferral is never a failure and never spends an attempt: `socialPostPublishRepository.releaseClaim` makes the target `pending` again at the deferral time and gives the attempt back (`attemptCount - 1`), under the claim's lease. Order:
1. **Paused** destination (`PublishDestination.pausedUntil` in the future): defer to `pausedUntil`.
2. **Daily cap**: Instagram and Threads read the live quota through `SocialPublisher.getPublishingLimit` (cached about 5 minutes per destination in Redis; a failed call falls back to the documented number), every network also counts our own published targets of the destination in the last 24 h (`socialPostPaceRepository.listPublishedSince`; Facebook Reels are counted apart from feed posts). Over the cap: defer to when the oldest counted publish leaves the window (never fail).
3. **Provider slots** (`concurrencySlots`, a Redis sorted-set semaphore in `packages/redis`): at most N jobs per network at once across all workers; a full network defers 30 to 60 s. Slots expire with the lease, so a crashed worker frees its slot. Redis being down fails open.
4. **Spacing**: one guarded `UPDATE "PublishDestination" SET "lastPublishStartedAt" = now WHERE id = ... AND ("lastPublishStartedAt" IS NULL OR "lastPublishStartedAt" <= now - gap) RETURNING id` (`reservePublishSlot`). Zero rows means another publish started inside the gap: the target is deferred to `last + gap + jitter` and the provider slot is given back. The row lock makes two workers racing on one destination safe: exactly one wins (tested on a real database).

Scope and limits of the gate: it covers a head's first attempt. Instagram and Threads create the container then and `media_publish` / `threads_publish` runs in the recovery step seconds to minutes later, so the cap is enforced at container creation (best effort at the boundary). Follow-up parts (thread replies, first comment) are not part of the daily cap, but a Threads reply is gated on its own quota: before the marker, `getReplyLimit` reads `reply_quota_usage` and `reply_config.quota_total` of `threads_publishing_limit` (documented fields only, cached about 5 minutes); when used up the part's claim is given back (`releaseClaim`, no attempt spent) and it is due again an hour later. An unreadable quota lets the part go ahead. Threads removals check `delete_quota_usage` / `delete_config` (100 per rolling 24 h) before the delete call; when used up the removal is refused with `removalQuotaExhausted` ("reached the network's limit of deletes per 24 hours") and nothing is sent. Parts share the error handling below.

**Errors** (`packages/utils/src/meta-graph-errors.ts` is used only by the Facebook, Instagram and Threads publishers, so its categories change nothing for comment automation or inbox sends). A limit answer carries a `scope`: **account** (the destination itself: 17 user, 80001 Pages, 80002 Instagram, 368 "temporarily blocked for policies violations" with a 6 h wait because Meta says only "wait", Instagram 9 / 2207042 daily limit, TikTok `spam_risk_too_many_posts`, `spam_risk_too_many_pending_share`) or **app** (the whole app: 4, 32, 341, 613) or **token** (TikTok `rate_limit_exceeded`, a per-minute throttle: short retry, no destination pause, no ladder step). Graph 506 (duplicate post) is `payloadInvalid` with `errorCode` `duplicatePost`: the guide says duplicate posts cannot be posted consecutively, so an identical post may already be live (for example from an earlier attempt whose answer was lost); the message says so and tells the person to check the page. 368 moved from `permissionDenied` to `rateLimited`; 341, 80001 and 80002 were added. Instagram 4 / 2207051 (suspected spam) and 25 / 2207050 (account restricted) are the category `accountRestricted`: the credential is fine, so no reconnect is recorded. The reset hint of `X-Business-Use-Case-Usage` (the longest `estimated_time_to_regain_access` of any bucket, minutes converted by `maxBucRegainMs`; the parsers moved to `packages/utils/src/meta-usage.ts`, `integrations/messenger/src/apis/usage.ts` re-exports them) or an exhausted `X-App-Usage` (15 min, our default; the header carries no time) rides on the failure as `retryAfterMs`; the next attempt is `max(ladder, hint)` capped at 24 h.

**Backoff.** A limit answer retries after 1 h, 2 h, 4 h (+ up to 5 min jitter) with its own budget (`rateLimitAttempts`, reset by a manual retry) and gives its attempt back; the network-error ladder (1, 5, 15, 60 min, 5 attempts) is separate. After the third wait the target fails with `errorCode = publishRateLimitExhausted` (a `postFailed` notification goes out as for any failure).

**Circuit breaker** (per destination, `socialPostPaceRepository.recordLimitError`). Only an account-level limit, restriction or spam answer counts (an app-level one backs the target off and pauses nothing). The second consecutive one sets `pausedUntil` and `pauseReason`: 6 h for `limitReached`, 24 h for `accountRestricted` and `spamRisk` (our defaults). Due targets of a paused destination are deferred to `pausedUntil`, never failed. A published post resets the counter and clears the pause. A different answer from the network (not an account-level limit) also resets it, but a `token` or `app` throttle and a transport error do not, so account limit, throttle, account limit still pauses. `pausedUntil` / `pauseReason` are in `GET /v1/posts/destinations` (only while the pause is still running) and shown as a small hint in the Connect row and the composer picker. No push notification is sent for a pause: the existing post notifications (`postFailed`, `postNeedsReview`) are per target and carry no destination payload, so a pause would need a new notification type; skipped on purpose.

**Counter semantics.** `consecutiveLimitErrors` counts consecutive account-level limit answers. Any other settled answer from the network (success, or a failure that is not an account-level limit) resets it; an app-level or token-level throttle, like a transport error, keeps it (`resetLimitStreak`; a success also clears the pause through `resetLimitErrors`); a transport `networkError`, an app or token throttle, a deferral and a cancellation never reached the network's decision and leave it alone. So limit, invalid media, limit does not pause, while limit, limit does and so does limit, throttle, limit. Applying a pause also restarts the counter, so the first limit answer after the pause ends does not re-pause at once.

**Platform-wide slots and the cap's race.** The provider slots (Facebook 3, Instagram 2, Threads 2, TikTok 1) are shared by every workspace: key `post-publish:slots:<provider>`. Throughput is bounded by the slot count over the time one attempt holds a slot, so with TikTok at 1 slot every TikTok publish on the platform runs one at a time and the others defer 30 to 60 s. The daily cap check is not atomic with the spacing booking: a burst can pass the cap check together and exceed it by the number of publishes in flight, which the minimum gap per destination bounds (one start per gap).

**Feeds.** Queue-mode feeds no longer need a posting schedule: a destination that has none gets `SchedulePlan.autoSpacing` placement (`listAutoSpacedSlots`): the earliest free instants that keep the network's minimum gap from every queued slot, recent publish and the last publish start, stay under the rolling 24 h cap, and wait out a pause. Items of one burst therefore get distinct slots. A destination that has a posting schedule keeps following it exactly as before, and a person or agent asking for `queue` on a destination with no schedule still gets the 422, so they set posting times. A feed's own daily cap is also capped by the smallest per-destination cap of its destinations. The pace gate remains the authority at publish time: it defers whatever placement misjudged.

## Scheduling

A post goes out at a time (`scheduledAt`) or from a destination's queue (see "Posting schedule"). Both are written to the **target**: `scheduledAt` (what the person asked for) and `nextAttemptAt` (the pipeline's clock) are written **in the same statement** by every schedule, reschedule and queue operation, so the due-target scan (`SocialPostTarget_due_idx`) and the minute cron pick it up with no extra job. A retry changes only `nextAttemptAt`.

- **Ask for a time.** `POST /v1/posts` and `PATCH /v1/posts/{id}` accept `scheduledAt` (ISO 8601 **with an offset**, e.g. `2026-12-01T09:00:00+07:00`), a `scheduledAt` per target, `queue: "next" | "top"` (or `publish: "queue"`, same as `next`), and `timezone` (IANA, default `Workspace.timezone`). The instant comes from the offset; the zone is stored on the target (`timezone`) to display it and to follow the queue. `publish: "now"`, `"draft"`, a time and a queue contradict each other (422). Guard: at least 2 minutes ahead and within one year (422 on `scheduledAt`). The content must pass the same check as publishing (422 `socialPostContentInvalid`, every issue listed); a create is refused before anything is saved. The post and its schedule are written in **one transaction** (`afterWrite` hook of `socialPostService.create` / `update`, built by `socialPostScheduleService.prepare`): content check, window, queue availability and the slot writes all run inside it, so a schedule that cannot be applied (for example a queue with no posting schedule; feeds are the exception, see "Publishing pace and platform limits") leaves no draft, and an update keeps the post as it was. A repeat of an idempotent create that finds a plain draft made by an earlier request applies the dispatch it asks for to that draft: `publish: "now"` publishes it (the same `publishNow` path), a time or a queue schedules it, `draft` leaves it; a post that is no longer a plain draft is returned as is, never a second post. The idempotency hash covers the content, not the dispatch (publish, time, queue, repeat), so a retry with another schedule is not a 409; only changed content is (409).
- **Status.** A scheduled post is `scheduled`; its targets stay `pending` with `scheduledAt` / `nextAttemptAt` set. When part of it has published and a later destination still waits, the post is `scheduled` again (not `publishing`). `socialPosts.list` / `get` return the post's `scheduledAt` (the earliest target time: published, else scheduled) and per target `scheduledAt`, `queueSlotAt`, `timezone`, `scheduleMode`, `status`, `provider`, `destination`.
- **List filters.** `bucket` (see "Buckets and counts"), `from` / `to` (UTC instants) keep a post when **any** target's effective time (`COALESCE(publishedAt, scheduledAt)`) falls in the range; `statuses[]`, `providers[]`, `destinationIds[]`, `inboxIds[]`, `topicIds[]`, `search` and the keyset cursor (ordered by creation) are unchanged. Drafts (no time) never match a time range.
- **Reschedule.** `POST /v1/posts/{id}/reschedule` (`targetId` for one destination, else every pending one) takes exactly one of `scheduledAt` (+ optional `timezone`), `queue` (`next` | `top`), `timezone` alone, or `unschedule: true`. It runs in one transaction under the post row lock and is **all or nothing**: each write is a conditional UPDATE that needs the target still `pending`, never attempted (`attemptCount = 0`) and not due within 1 minute; one target that fails the test refuses the whole call with 409 `socialPostTargetNotReschedulable` (a post with nothing waiting too). `timezone` alone keeps the wall clock: the old wall clock is read in the old zone and resolved in the new one with `resolveZonedInstant` (same daylight-saving policy as broadcasts: an ambiguous time takes the earlier instant, a skipped one moves forward); a queued target refuses it (its time follows the posting schedule). `POST /v1/posts/{id}/unschedule` (`socialPosts.unschedule`, `{id, targetId?}`; repeating it on a post that is already a draft returns the post unchanged) is the same operation as `reschedule` with `unschedule: true`, on its own route so the trial-expired gate (which keys on the path) can let it through. `unschedule` clears `scheduledAt`, `nextAttemptAt` and `queueSlotAt` and makes the post a `draft` again.
- **Cancel.** `DELETE /v1/posts/{id}` on a `scheduled` post cancels the waiting targets (`cancelled`, queue time freed in the same UPDATE) and keeps the post as history (`cancelled`, or `partiallyPublished` when some targets already went out).
- **Edit.** A post is frozen once any target is not `pending`. A destination added to a scheduled post takes the time of its earliest waiting destination, as a custom time.
- **Late publish.** Every minute, before due targets are handed to the queue, `socialPostScheduleService.failMissed` (in the `enqueueSocialPostTargets` tick) looks at pending targets whose `nextAttemptAt` is more than 6 hours in the past: they become `failed` with `errorCategory`/`errorCode` `missedSchedule` (queue time freed, post recomputed). Later than the cutoff but within 6 hours: published late as usual. The clock is `nextAttemptAt`, so a retry waiting out its back-off is not "late", and a manual retry (due now) never is. The due scan (`claimDue`) never moves that clock: it marks a queued target with `leaseExpiresAt` (null on every pending target otherwise; the mark is skipped by later scans until it passes) so a dropped job (a blocked owner) is re-queued after 5 minutes without hiding how late the target is. A trial-expired workspace's due targets are not published, so after 6 hours they fail the same way, however many scans passed meanwhile. The cutoff is also part of the due scan and of the claim (`lateCutoff`, one constant `MISSED_SCHEDULE_WINDOW_MS` through `lateCutoffAt`): a target older than the window is never queued or claimed, so a backlog larger than one sweep batch (100) cannot publish late while it waits to be failed, and a job queued before an outage cannot publish a target that has become too late. The due scan, the recovery scan and the part scans claim batch after batch until a batch comes back short or a 40 second budget is spent (`claimInBatches`); every claim moves the row's marker past now, so a blocked owner's rows cannot hold the head of the line and a backlog drains within the tick.
- **Trial expired (invariant 14).** Scheduling, rescheduling to a time or queue, re-zoning and editing the posting schedule answer 403 `trialExpired` (or `macLimitReached`); cancelling (`DELETE`) and `POST …/unschedule` stay allowed (`reschedule` is refused there, even with `unschedule: true`) because they only take work away.
- **Errors.** 409 `socialPostNotSchedulable` (post is not a draft/scheduled post, or a target already left `pending`), 409 `socialPostTargetNotReschedulable`, 422 on `scheduledAt` / `timezone` / `queue`.

## Recurring posts

A post repeats by being the **template** of a series: it stays a `draft` for good and is never published itself. At each run of its rule a copy is made and scheduled for that run's time. Nothing is shared with the broadcast tables or services; only the rule (`recurrenceRuleSchema`), its date arithmetic (`packages/utils/src/recurrence.ts`) and the form (`RecurrenceRuleFields`) are reused.

- **Data.** `SocialPostRecurrence` (one per template: `rule`, `nextRunAt`, `accountedThroughAt`, `occurrenceCount`, `pausedAt`, `endedAt`; partial index `(nextRunAt, id) WHERE endedAt IS NULL AND pausedAt IS NULL` serves the due scan) and the ledger `SocialPostRecurrenceOccurrence` (`localSlot` text `YYYY-MM-DD HH:mm` in the rule's zone, `occurrenceAt`, `outcome` `created | skipped | missed | excluded`, `socialPostId` SET NULL; unique `(recurrenceId, localSlot, occurrenceAt)`, the same key as the broadcast ledger, so a zone edit or a daylight-saving change that makes one text name two instants, or two texts one, never collides or duplicates). A copy carries `parentSocialPostId` and `occurrenceAt` (unique per template and instant).
- **Materialiser.** Minute cron `materializeSocialPostRecurrences` (schedule queue, second 12, lock `schedule:materialize-social-post-recurrences`, 500 series per tick). Per series, `socialPostRecurrenceService.materializeSeries` settles at most 10 slots, each in its own transaction: lock the template post row, then the series row (the post pipeline's order: post, destination advisory locks, targets), insert the ledger row (a unique-key conflict means a replay: nothing is made again), clone and schedule the copy inside a savepoint, then advance `nextRunAt` with a compare-and-set on the slot. `afterOccurrences` counts only `created`. A blocked owner's series is skipped by the worker without advancing (`isBlockedWorkspace`); because skipped series stay due, the tick pages through the due list with a keyset cursor (`(nextRunAt, id)`, up to 10 pages of 500, stopping once 500 non-blocked series were handled) and resumes where it stopped on the next tick, so blocked series cannot starve the active ones; its slots are accounted as `missed` once the owner is back and the window has passed.
- **Outcomes.** `created`: a copy was scheduled (custom mode, the series' zone, `scheduledAt = nextAttemptAt = slot`; a slot that is a few seconds past is published on the next scan, so the 2-minute lead of a manual schedule does not apply). `excluded`: the local date is in `rule.excludeDates`. `missed`: the slot is later than 6 hours minus a 5-minute margin (the pipeline gives a target up 6 hours after its time, so a copy made at the very edge would be failed before it could go out). `skipped`: the template could not be published as it stands (a destination was disconnected, a file removed; any business rule error from the clone or the schedule check rolls back only that savepoint) or is no longer a draft. Any other error rolls the slot back and it is retried on the next tick.
- **Cloning.** `cloneSocialPostInTx` (`packages/business/src/social-post/clone.ts`) is the one copy routine: text, link, destinations (content type, options, text override), shared and per-destination files, topics; no schedule, result or idempotency key. `duplicate` and the materialiser both call it.
- **Editing.** Editing the template changes only the copies not made yet; editing, rescheduling or cancelling one copy changes only that copy. A template cannot be published, scheduled or rescheduled while its series is running (409 `socialPostIsRecurringTemplate`). A new rule replaces the old one and starts a new count; runs before now are not made up. Pausing keeps the rule: resuming continues from the next run after now, and the runs of the pause are not made up. Ending is final for the series (the template can be given a new rule).
- **Skip and restore.** A skipped date is added to `rule.excludeDates` under the series lock; the series keeps running and the scan records the slot as `excluded`. A date that already has a ledger row cannot be skipped or restored (409 `socialPostOccurrenceSettled`); a date with no run is a 422.
- **API.** Public (scope `posts`): `setRecurrence` (PUT `/v1/posts/{id}/recurrence`), `endRecurrence` (DELETE), `pauseRecurrence`, `resumeRecurrence`, `listOccurrences` (GET `…/recurrence/occurrences`), `skipOccurrences`, `restoreOccurrences` (POST `…/recurrence/occurrences/skip|restore`); `recurrence` is also accepted by `create` and `update` (not with a time, `publish` or a queue) and returned on the post with its `upcoming` runs. Session twins `private{End,Pause,Resume}SocialPostRecurrenceAPI`; setting a rule, listing, skipping and restoring runs have no session twin until the page offers them (they are public only). Setting, resuming, skipping and restoring are refused with 403 `trialExpired` in a workspace whose plan has expired; pausing and ending stay open (the pause path is on the gate's allow-list in `authorize-workspace-access.ts`, `DELETE` is open by method).
- **Not copied by templates**, and purged child-before-parent (ledger, series, then the posts): see the workspace-purge table list.

## Posting schedule

`PublishDestinationSchedule` (one row per destination, created when someone sets it; `workspaceId` and `publishDestinationId` `ON DELETE CASCADE`, unique on the destination) holds the destination's weekly posting times: `timezone` and `slots`, seven items `{weekday, enabled, times: ["HH:mm"]}` (`0` = Sunday … `6` = Saturday, at most 10 times per day, local times so the clock survives a daylight-saving change). A destination with no row has every day off.

- **API.** `GET|PUT /v1/posts/destinations/{id}/posting-schedule` (procedures `getPostingSlots` / `updatePostingSlots`) and `GET /v1/posts/destinations/{id}/free-slots?after&limit` (router `publishDestinations`, scope `posts`; CLI `post-destinations posting-schedule get|update`, `post-destinations free-slots list`). The Posts page has no session twin for these: it does not read or edit the schedule yet, so only agents call them (a UI that needs one adds the twin over the same operations). The destination must belong to the workspace (404 otherwise). A destination that is not `ready` can still hold a schedule; its queued posts wait for it to be ready.
- **Free times.** `listFreeSlots(schedule, occupied, after, count)` (`packages/utils/src/posting-slots.ts`, pure) resolves each local time day by day with the broadcast daylight-saving policy, skips disabled days and occupied instants, and stops after 366 days. Case-table test: `packages/utils/__tests__/posting-slots.test.ts`.
- **The queue.** A target with `scheduleMode = 'queue'` holds a slot: `queueSlotAt = scheduledAt = nextAttemptAt` = a posting time at least 2 minutes ahead and within a year. `queue: "next"` takes the first free time; `queue: "top"` takes the first time and pushes the destination's other queued posts one free time later (all in one transaction); leaving the queue (a custom time, unschedule, cancel, a final state) frees the slot.
- **Locking.** Every operation that touches a destination's slots (add to queue, top, remove/switch to custom, unschedule, cancel, edit the schedule, change its zone) takes `pg_advisory_xact_lock(hashtextextended('social-post-queue:<publishDestinationId>', 0))` first, in destination-id order, then the target rows. The partial unique index `SocialPostTarget_destination_queueSlotAt_key (publishDestinationId, queueSlotAt) WHERE queueSlotAt IS NOT NULL` is the second barrier: a path that forgets the lock fails instead of double-booking. A target that becomes `published`, `failed` or `needsReview` (and a retry or "mark as published") clears `queueSlotAt` in the same UPDATE that records the state. `publishNow` clears the slot too and does not take the lock (clearing cannot double-book).
- **Editing the schedule.** `PUT` replaces `slots` / `timezone` and re-seats the queue in the same transaction (all or nothing; a conflict anywhere rolls everything back): a queued target keeps its slot when it is still a posting time (after a zone change: the same wall clock in the new zone, when that is a posting time), else it takes the next free time in its old order; a target left with no time stops being queued, keeps `scheduledAt` as a `custom` time, and is listed in `reflow.detached`. A target due within a minute is never touched. The result is `{schedule, reflow: {keptCount, moved[], detached[]}}`.
- **Purge.** The workspace purge drains the schedules (with the feed and target-set destination rows) child-before-parent in bounded batches before the targets and the bindings; targets are drained before destinations (RESTRICT). Not copied by templates (tied to a connected channel or account).
- **Indexes.** `SocialPostTarget_destination_queueSlotAt_key` (above) and `SocialPostTarget_workspaceId_scheduledAt_idx (workspaceId, scheduledAt) WHERE scheduledAt IS NOT NULL` (calendar). The EXPLAIN test (`packages/business/__tests__/integration/social-post-scheduling-db.test.ts`) checks the queue lookup is served by an index and the unique index definition.

Not verified or open: the calendar range filter uses `COALESCE(publishedAt, scheduledAt)`, which the partial index on `scheduledAt` cannot serve (the workspace index does the narrowing); lock order is one rule everywhere: post row first, then the destinations' advisory locks, then the target rows (publish result, retry, resolve, cancel, schedule, reschedule and the missed scan all follow it; the posting-schedule edit takes the advisory lock and the target rows but never the post row, so it cannot close a cycle). Unit tests pin the order for the publish result, retry and resolve.

## AI writing

`POST /v1/posts/ai/generate` (scope `posts`; session twin `socialPostsAiAPIs.privateGeneratePostTextAPI`, `broadcast` permission) returns suggested plain text. **Nothing is saved or published**: the caller puts the text into a post. UI and API call the same function, `generatePostText` (`features/social-posts-ai/lib/generate-post-text.ts`).

- **Modes.** `write` (from `brief`), `rewrite`, `shorten`, `expand`, `tone` (needs `tone`), `fit` (needs `destinationIds`). `destinationIds` only supply the limit: the shortest documented text limit over the networks of those destinations (the registry, `postTextLimitFor`; units are UTF-16 code units like the registry's own check). The answer is cut to it without splitting a character and `truncated` says so. Hashtag and first-comment suggestions are not built (a first comment belongs to the parts work).
- **Model and key.** The workspace's own AI integration, resolved with `resolveTranslationModel` on every call (it checks the integration is this workspace's, enabled and usable). The caller may pick it: `integrationId` + `model`, both or neither (zod refine). `integrationId` is a connected provider name (`openai`, `gemini`, `claude`, `deepseek`, `openrouter`, `muse`; one integration per provider per workspace) or the id of an OpenAI-compatible integration (digits); `modelConfigFromChoice` (`features/social-posts-ai/model-choice.ts`) turns it into the `modelConfig` AI agents store. Without a pick, the model chosen for Inbox translation (`InboxTranslationSettings.modelConfig`, read whether or not translation is switched on) is used. There is no separate "AI for writing" setting and no `SocialPostAiSettings` table. Neither a pick nor a translation setting: 409 `aiModelNotChosen`; an integration that is gone, disabled, another workspace's or invalid: 409 `aiNeedsReconfiguration`. The pick is part of the idempotent request (another model with the same key is 422 `aiKeyReused`). The model id itself is not checked against the provider's model list: a model the provider refuses surfaces as `aiProviderError`. No platform credit or quota is charged (none exists for AI text; **UNVERIFIED**: only a grep of `quota-enforcement` was done).
- **Idempotency (required `idempotencyKey`).** Before any provider call the key is reserved atomically (Redis `SET NX`, key `postai:<workspaceId>:idem:<sha256(key)>`, value holds the request hash). A repeat with the same request returns the stored result, or replays the stored provider failure, for 10 minutes without a second paid call; while the first call runs (30 s claim) it answers 409 `aiRequestInProgress`; the same key with another request is 422 `aiKeyReused`. Only provider failures (`timeout`, `rateLimited`, `integrationUnavailable`, `providerError`, `emptyOutput`) are remembered; a refusal before the call (no model, a cap, a busy actor) frees the key.
- **Caps.** One call at a time per actor (the member, or one shared guard for tokens; `postai:<ws>:busy:<actor>`, 30 s), 30 per minute and 500 per day per workspace (`incrWithWindow`, fixed windows, keys expire with their window), counted only for calls that reach the provider. Past a cap: 429 `aiRateLimited`.
- **Prompt safety.** No tools or function calling. The system prompt says everything between marker lines is untrusted data; the mode, tone, language and limit come from closed values the server chose; the text and brief are placed only inside `=====BEGIN TEXT=====` / `=====BEGIN BRIEF=====` blocks, and runs of `=====` inside them are collapsed so they cannot imitate a marker. Output: control characters removed, trimmed, clamped; rendered as text in the composer. The provider is told not to store the request (`openai.store: false`). Logs carry counts, mode and elapsed time, never the prompt or the answer.
- **Errors.** 402 `workspaceBlocked` (trial expired: it spends the workspace's key), 409 `aiModelNotChosen` / `aiNeedsReconfiguration` / `aiRequestInProgress`, 422 `aiKeyReused`, 429 `aiRateLimited`, 502 `aiProviderError` / `aiEmptyOutput`, 504 `aiTimeout` (15 s provider abort).
- **Composer.** "Write with AI" (`components/ai-assist.tsx`): an AI integration and model picker on top (the flow AI step's model select; the last choice is remembered per workspace in `localStorage`, `composer-ai-model:<workspaceId>`; one integration is picked automatically; with none, a link to Settings > Integrations and Generate is disabled), a mode select, a brief (or the post text for the editing modes), a suggestion preview, and Insert at the end / Replace post text. It never applies on its own; a fresh `idempotencyKey` is made per click. A privacy line says the text is sent to the provider chosen in the picker. `actions/list-ai-integrations.action.ts` lists the usable integrations (connected providers and enabled OpenAI-compatible ones).
- **Network style, options and several options (one model call).** `providers` (`facebook`, `instagram`, `threads`, `tiktok`; deduped and sorted; default: the networks of `destinationIds`) selects a fixed style guide per network (`POST_WRITER_NETWORK_GUIDES` in `packages/ai/src/server/services/post-writer.ts`: Facebook 2 to 4 short story-like paragraphs ending with a question; Instagram strong first line, hashtags at the end, "link in bio" instead of a pasted link; Threads 1 to 3 conversational sentences, at most 500 characters; TikTok short caption with trending-style hashtags). One network: its guide. Several: "suitable for all" unless `perNetwork: true`, which returns one version per network (`variants[].provider`; `variants` is then ignored). Toggles `hashtags`, `emoji`, `callToAction` and `callToActionText` (up to 80 characters, untrusted: it goes in a `=====BEGIN CTA=====` block); omitted toggles default to hashtags on when any network is Instagram or TikTok, emoji on, call to action off (`features/social-posts-ai/lib/writing-defaults.ts`; the resolved values are part of the idempotent request). The hashtag count comes from the network guide. Mode `hashtags` returns only `hashtags` (up to 8, each with `#`) for the `text`. `variants` (1 to 3) returns that many different options from one call. The model is asked for JSON (`{"variants":[{"text"}]}`, per network `{"provider","text"}`, via the `ai` SDK's structured output) and the answer is parsed leniently (`parsePostWriterOutput`): code fences are stripped, a malformed answer is used whole as one variant, and JSON of another shape is never returned as text (it is an `aiEmptyOutput`). Max output tokens: 800 per version, capped at 2400. The quota counts per model call, not per variant. Each variant is cut to its own network's limit (a plain one to the shortest) and flagged with `truncated`. Response: `{ variants: [{ text, provider, limit, truncated }], hashtags, text, limit, truncated, usage }` where `text` is the first variant (backward compatible).
- **Composer options.** The popover has Hashtags / Emoji / Call to action switches (with a wording field), an options count (1 to 3) and, when two or more networks are selected, "Write per channel". Hashtags default per network; the choices are remembered per workspace in `localStorage` (`chatbotx:post-ai:<workspaceId>`, read and written in try/catch). Each option is a card with Insert at the end / Replace post text; per-network cards offer "Apply to <network>" and a combined "Apply to each channel", which sets each target of that network to "Customise for this channel" with the version as its text (`applyTextPerProvider` in `lib/composer-state.ts`). Mode `hashtags` shows clickable chips that append to the shared text.
- **MCP / CLI.** Classified as an ordinary write (default confirmation); CLI `social-posts write-with-ai`.

## Composer: per-channel time and files, runs, sets, performance

- A target card has "Separate time for this channel" (a time of its own, 2 minutes to 1 year ahead, read in the workspace zone; sent as the target `scheduledAt`) and, when customised, "Different files for this channel" (an empty list publishes without files; `null` follows the shared files). A draft keeps no own times (`withoutTargetTimes`).
- The repeat control of a series lists the upcoming runs with Skip / Restore and the past runs with their outcome (private twins of `listOccurrences`, `skipOccurrences`, `restoreOccurrences`).
- A published composed post shows a Performance panel per destination (private twin of `GET /v1/posts/{id}/metrics`).
- The target-set picker renames a set and chooses its members (private twin of `postTargetSets.update`).

## Snippets and target sets

Reusable post text and saved destination selections. Neither is copied by templates (invariant 27): a set points at external accounts, and the other Posts resources are not copied either, so a copied snippet would arrive without a use; no Tools card, no `TOOL_TEMPLATE_COVERAGE` entry.

- **Tables.** `SocialPostSnippet` (`kind` signature | hashtags | text, `name`, `content`, `position`; unique `(workspaceId, name)`), `SocialPostTargetSet` (`name`; unique `(workspaceId, name)`) and `SocialPostTargetSetDestination` (primary key `(targetSetId, publishDestinationId)`, `position`, `workspaceId`, an index on the destination). FKs: every table `workspaceId` -> `Workspace` CASCADE; `TargetSetDestination.targetSetId` -> `TargetSet` CASCADE; `.publishDestinationId` -> `PublishDestination` CASCADE (a destination that goes away drops out of its sets; no RESTRICT). Drained in bounded batches by the workspace purge before the targets and bindings. Caps: 100 snippets and 50 sets per workspace, 30 destinations per set, 2000 characters per snippet; the cap is checked under an advisory lock (`post-snippets:<ws>`, `post-target-sets:<ws>`).
- **Formats.** RSS 2.0, RSS 1.0, Atom and JSON Feed 1 and 1.1 (`version` `https://jsonfeed.org/version/1[.1]` or the `www.` form; content type `application/feed+json` or `application/json`; `items[].id`, `url`, `title`, `summary`, `content_text`, `content_html`, `image`, `banner_image`, `date_published`), with the same 2 MB / 10 s / SSRF limits. The parsed item carries its author, categories, plain-text full content, every raw field and its picture candidates (see "Dynamic content"). The alternate-link hint accepts `application/feed+json` too.
- **Write with AI (`aiWrite`).** Per feed: `aiWrite`, `aiInstructions` (at most 300 characters, untrusted: sent to the model between markers as data), `aiIntegrationId` + `aiModel` (both or neither, checked on the pair the save leaves: a PATCH that names one half is validated against the stored other half and both are written together; neither uses the Inbox translation model). Each new item's text is written by the composer's writer, which receives the RENDERED TEMPLATE as its draft (the owner's template filled in with the item; the title, summary and link ride along as untrusted data) (`@chatbotx.io/ai/feed-post-writer` -> `generatePostText` of `post-writer`) through `socialPostAiService.generate`, so the workspace's AI rate limits (30 per minute, 500 per day), the idempotency replay (key `feed-post:<feedId>:<itemKey>`) and the cut to the shortest network limit all apply; one shared text for every network (no per-network versions in this release). The writer lives in `@chatbotx.io/ai`, which depends on this package, so it is injected like the fetcher (`registerFeedPostWriter`, registered by the worker and the builder's Node route handlers). The link is appended when the model leaves it out; the signature is appended as for a template. On any AI problem (no integration, rate limit, provider failure, empty output) the text template is used and the item is recorded `created` with `reason = aiFallback`; a feed is never blocked by the model. `aiIntegrationId` + `aiModel` must resolve inside the workspace (the writer's `resolveTranslationModel`): create and update refuse a foreign or unusable one with 422 `validation` on `aiIntegrationId` ("AI integration not found."), and generation checks it again, so a stale id falls back to the template.
- **First check (`postLatestOnFirstCheck`).** Default false. When true, the first check records every item as before except the newest, which goes through the normal creation path (template or AI, `mode`, destinations); the others are `skippedOld`/`existing`. Changing the feed address starts over with a new first check.
- **Send test.** `POST /v1/post-feeds/{id}/test` (session twin `privateSendPostFeedTestAPI`; Feeds page button "Send test"): fetches the feed, builds the post from the newest item exactly as a check would (template or AI, signature, destinations) and saves it as a DRAFT (`createdVia = feed`), whatever the feed's `mode`. It never publishes or queues, and never writes the item ledger, so the item still becomes its normal post later. Returns `{ socialPostId, note }` (`note = aiFallback` when the template was used instead of AI). 10 per hour per workspace (429 `feedTestRateLimited`), 422 `feedHasNoItems`, `feedNotParseable`, `feedUnreachable`; refused in a trial-expired workspace.
- **Create a post from an item.** `GET /v1/post-feeds/{id}/items/{itemId}/draft-content` (session twin `privatePostFeedItemDraftContentAPI`) returns `{ text, linkUrl, imageUrl, title }`: the feed's text template applied to the item (no AI, nothing is spent), its link and its picture. The item is found by ledger id in the feed and workspace (404 otherwise) and read again from the feed; one that has left the feed keeps only the stored title and link. The Items dialog's "Create post" opens `/posts/create?fromFeed=<feedId>&fromFeedItem=<itemId>`: the composer resolves the ids through that procedure (nothing but ids is in the address), fills the text and link, and adds the picture as a media file by URL, imported by the media-by-URL path with its SSRF guard when the post is saved. Agents do the same with `socialPosts.create` (`text`, `linkUrl`, `media: [{ url }]`).
- **API (scope `posts`).** `/v1/post-snippets` (`GET`, `POST`, `GET|PATCH|DELETE /{id}`) and `/v1/post-target-sets` (same). Duplicate name: 409 `snippetNameTaken` / `targetSetNameTaken`. Create and update are refused in a trial-expired workspace (403 `trialExpired`); list, get and delete stay open. A set is read with each destination's `state` (the publishing states: `ready`, `needsReconnect`, `permissionMissing`, `inboxDisconnected`); applying a set re-checks every destination, so the composer selects only the ready ones and reports how many it skipped. There is no `targetSetId` shorthand on `POST /v1/posts` (an agent reads the set and passes its ready destinations as `targets`).
- **Signature.** `POST /v1/posts` takes an optional `signatureId` (a snippet of kind `signature`). The operation layer (`socialPostOperations.create`) appends its text to the shared `text` once, after a blank line, before the post is stored, and refuses a result longer than the post text limit (422 `signatureId` / `text`). It is create-only: the stored text is what is published, nothing is appended at publish, and an update never appends again (so a retried update cannot double it). Destinations with a `text` of their own do not get it. An idempotent repeat of the same create with the same `signatureId` finds the same stored text.
- **Composer.** `components/snippet-picker.tsx` inserts text and hashtag snippets at the end of the text and chooses the signature (shown as a chip; only for a new post); `components/snippet-manager-dialog.tsx` lists, creates, edits and deletes snippets; `components/target-set-picker.tsx` applies a set (the selection becomes exactly its ready destinations), saves the current selection as a set and deletes sets.

## Feed auto-posting

A workspace registers an RSS or Atom feed; each check turns the items it has not seen into posts for the feed's destinations: drafts for a person to review (the default), or queued on each destination's posting schedule. Page: Posts > Feeds. Post text comes from a template over the item's fields; pictures named by the feed (and, when the feed asks for it, the item's article page) are imported, checked and attached (see "Dynamic content").

- **Tables.** `SocialPostFeed` (`workspaceId` CASCADE, `name`, `feedUrl` unique per workspace, `status` active | paused | error, `intervalMinutes` default 60 (15-1440), `nextCheckAt`, `leaseExpiresAt`, `lastCheckedAt`, `lastManualCheckAt`, `etag`, `lastModified`, `consecutiveFailures`, `lastErrorCode`, `textTemplate`, `templatesByProvider` (jsonb strict record keyed by the provider enum, NOT NULL default `{}`), `fetchArticleImage` (boolean, NOT NULL default false), `templateSyntax` legacy | v2 (DB default `v2`; `legacy` is the old `{title}` renderer, still accepted by the API), `lastRunSummary` (jsonb, NULL until the first check: the last check's `kind` checked | notModified | stale | failed, `items`, `fresh`, `created`, `refused`, `waiting`, `staleRetries`), `mediaMode` auto | field | none (DB default `none`, new feeds `auto`), `mediaField`, `mediaLibraryFileIds` (jsonb, default `[]`), `postAs` photo | link | text (DB default `text`, new feeds `photo`), `noImageFallback` link | text | skip (DB default `text`, new feeds `link`), `filters` (jsonb, null = none), `signatureId` -> `SocialPostSnippet` SET NULL, `mode` draft | queue, `aiWrite` (default false), `aiInstructions`, `aiIntegrationId`, `aiModel`, `postLatestOnFirstCheck` (default false), `maxItemsPerRun` default 5, `dailyCap` default 10, `startedAt`, `primedAt`, `createdById` -> `User` SET NULL); `SocialPostFeedDestination` (`feedId` CASCADE, `publishDestinationId` CASCADE, unique per pair); the ledger `SocialPostFeedItem` (`feedId` CASCADE, `itemKey`, `title`, `link`, `publishedAt`, `outcome` created | skippedOld | skippedInvalid | skippedFiltered | skippedNoImage, `reason` (one code or a comma-separated list of notes), `imageUrl`, `imageSource`, `imageError`, `droppedDestinationIds` (jsonb), `socialPostId` -> `SocialPost` SET NULL; **unique `(feedId, itemKey)`**). Every FK has an index (the nullable ones partial), the due scan has `SocialPostFeed_due_idx (nextCheckAt, id) WHERE status = 'active'`. `SocialPost.createdVia` gains `feed`. Not copied by templates (invariant 27): an external URL and external accounts; no Tools card. The workspace purge drains `SocialPostFeedItem` (the one table that grows) in the heavy stage before the posts; the other two cascade. Caps: 20 feeds per workspace, 10 destinations per feed.
- **Why items wait.** The last-run summary (`lastRunSummary`) carries `waitingReason` when `waiting` is above 0: `dailyCap` (rolling 24 h cap, the smaller of the feed's and its destinations' caps), `runLimit`, `attempts`, `timeBudget` or `pictureBudget`. With `dailyCap` it also carries `dailyCap` and `nextSlotAt` (oldest counted post plus 24 h, ISO 8601). Rows saved before this have none of the three and show the generic "waits for the next check" line; the Feeds table shows "Daily limit reached ({cap} per 24 h) — N new items wait" plus the next free time.
- **Exactly once.** `socialPostService.createInTx(tx, input)` is the transaction-scoped core of `create` (which is a thin wrapper around the same steps): the ledger row (`ON CONFLICT (feedId, itemKey) DO NOTHING`) and the post are written in **one transaction**, so an item is turned into a post once, or nothing is written and the next check retries it whole. Two workers racing on one item: the loser's insert returns nothing and it creates no post. The idempotency key `feed:<feedId>:<sha256 of the item key>` is a second barrier. `createInTx` never downloads a file (a URL in `media` is refused): the feed's picture is imported BEFORE the transaction and only its Media Library id enters it. Only a refusal caused by the ITEM'S CONTENT is recorded as `skippedInvalid` (never retried for ever): `socialPostContentInvalid` (the publishing rules refuse the text or link for a network) with the specific issue codes in `reason`, e.g. `socialPostContentInvalid,textTooLong,tooManyLinks`, and the `prepareFeedPost` codes (`emptyText`, `textTooLong`, `templateError`, `noDestination`, `noDestinationAccepts`). Every OTHER refusal of a post (422 `validation` on `queue`/`scheduledAt`/`targets`, 402 `workspaceBlocked`, 409 conflict or `notSchedulable`, 429, a destination that went away) is a problem of the feed or its destinations that the same item would hit again: NO ledger row is written (the picture this run imported is discarded), the check STOPS (the same cause would repeat for the next items), the feed's `lastErrorCode` becomes `postRefused` (shown on the Feeds page), the failure counts toward the five that park the feed in `error`, and the next check retries the items while they are inside the 7-day window.
- **Check.** The minute cron `scanSocialPostFeeds` (offset 14 s, lock `schedule:scan-social-post-feeds`) claims the due active feeds (`FOR UPDATE SKIP LOCKED`, 20 per batch; a tick keeps claiming batches until none is due or 40 s have passed, so the platform is not capped at 20 checks a minute; the next tick goes on, and a tick that used its budget logs a warning), pushes each `nextCheckAt` forward by its interval in the same statement and enqueues one `postPublish` job `runFeed` (job id `social-post-feed-<id>`, BullMQ priority 100 so a feed check never waits ahead of a publish job). The job takes the feed's lease (10 minutes; a paused feed or a held lease is skipped), fetches, parses, writes the ledger and the posts, and stores the result only while the lease is still its own. An address change also clears `leaseExpiresAt`, so a check still running for the old address cannot write its validators, priming or counters over the reset, and every ledger or post write of a check runs in a transaction that first locks the feed row (`FOR SHARE`, `lockLease`) and aborts the check when it no longer owns its lease: the old address creates nothing after the edit. A check whose `finishRun` matched no row makes the feed due again at once (`markDue`), so the new address is checked at the next tick instead of an interval later. When the queue refuses a job, that feed is made due again; a batch where every job was refused stops the tick. A blocked owner's job is a bare return (`withBlockedOwnerGuard`); the cron itself does not look at plans. **First check primes:** it records every item the feed already has as `skippedOld` and creates no post; later checks only consider items newer than the feed's `startedAt` and no older than 7 days. New items are taken OLDEST first (inside that window), so a burst is posted in the order it was published; a check creates posts until `maxItemsPerRun` have been created or `dailyCap` per rolling 24 hours is reached, and a refused item does not use one of the places. Items beyond either limit are left unrecorded, so the next check takes them while they are still young; no outcome is recorded for them. Ledger rows older than 180 days are pruned (a pruned item that is still in the feed is re-recorded as `skippedOld`, never posted).
- **Fetching.** `net/feed-fetch.ts` (Node-only, its own package subpath; registered into `registerFeedFetcher` by the worker and by the builder's route handlers, invariant 25): `checkSsrfSafety` on the feed URL and on every redirect, the socket pinned to the vetted address (`pinnedGet`, no DNS rebinding), at most 3 redirects, 10 seconds in total, a 2 MB body cap (declared and streamed), the content type must be XML, a conditional GET with the stored `ETag` / `Last-Modified` (304 = success, nothing parsed). When a check leaves items waiting (per-check, daily or picture cap; they are not in the ledger), it stores no `ETag` / `Last-Modified` (both are cleared), so the next check re-reads the body instead of getting a 304 and the waiting items are taken as soon as capacity returns; the ledger still dedupes. Parsing is `fast-xml-parser` (a new dependency of `@chatbotx.io/business`, already in the lockfile through the AWS SDK; chosen over `linkedom`, which is a DOM and a worker-only dependency): a document that declares entities is refused, nesting is limited to 20, at most 100 items are kept. Text is HTML-stripped, control characters removed and bounded (title 300, summary 500, post 5000 characters); a link must be http(s).
- **Failures.** A fetch or parse failure stores `lastErrorCode` (`blocked`, `timeout`, `tooLarge`, `badStatus`, `badContentType`, `unreachable`, `tooManyRedirects`, `invalidFeed`, `internal`) and counts; the fifth in a row (`POST_FEED_MAX_CONSECUTIVE_FAILURES`) sets `status = error`, the paused-by-error state: the scan only picks `active` feeds, so an `error` feed is never checked again until a person resumes it (the page shows "Paused – feed error", the last error and a Resume button; no push yet). A success resets the counter. Resume sets it active again, clears `consecutiveFailures` and `lastErrorCode`, and schedules a check now.
- **Validate on save.** Create, and update with a changed `feedUrl`, fetch and parse the address first with the same guarded fetcher the preview uses (SSRF guard, pinned DNS, 2 MB, 10 s) and write nothing when it fails: 422 `feedNotParseable` (not an RSS or Atom feed) or 422 `feedUnreachable` (could not be fetched); an address the guard refuses stays `validation` on `feedUrl`. When the address is an HTML page that advertises `<link rel="alternate" type="application/rss+xml|atom+xml" href>`, `feedNotParseable` carries `data.suggestedUrl` (resolved against the page, http(s) only, vetted by the SSRF guard); the dialog shows it under the address field with a Use button. The preview raises the same codes. An unchanged address is not fetched again on update.
- **API (scope `posts`).** `/v1/post-feeds`: `GET` (optional filters `search` (case-insensitive, feed name or address), `status[]`, `mode[]`, `destinationIds[]` (feeds posting to at least one of them); strict query, every filter is a `workspaceId`-scoped predicate in the repository SQL, the destination one an `EXISTS` on `SocialPostFeedDestination`; the Feeds tab keeps them in the URL as `feedQ`, `feedStatus`, `feedMode`, `feedDestinations`), `POST`, `POST /preview {feedUrl, ...draft}` (fetches and returns the first 5 items with their detected fields; with a draft `textTemplate`/`postAs` also a `render` per item; stores and downloads nothing; the parsed items are kept 2 minutes so a draft can be re-rendered while typing: only a real fetch counts against 10 per hour per workspace, 429 `feedPreviewRateLimited`, drafts rendered from the kept items have their own 300 per hour; the other fetches of an outside address (create, a changed `feedUrl`, `GET .../draft-content`; on save it is the last step, after every cheap validation) share 60 per hour per workspace, 429 `feedFetchRateLimited`, and the draft-content one falls back to the stored title and link when it is limited), `POST /bulk-delete {ids}` (1 to 100 ids; deletes the feeds and their item history in one statement, returns `{ deletedIds, notFoundIds }`; ids outside the workspace are reported, not an error; stays open in a trial-expired workspace via the gate's POST allow-list; session twin `privateBulkDeletePostFeedsAPI`; the Feeds tab's checkboxes and "Delete selected" use it), `GET|PATCH|DELETE /{id}`, `POST /{id}/pause`, `POST /{id}/resume`, `POST /{id}/test` (send test), `GET /{id}/items/{itemId}/draft-content`, `POST /{id}/check` (run now: at most once per 5 minutes, 409 `feedCheckCooldown`; 409 `feedCheckInProgress` when a check of the feed is already waiting or running, and the cool-down is not spent; 409 `feedNotActive` for a paused feed) and `GET /{id}/items` (keyset cursor). CLI `post-feeds list | create | preview | bulk-delete | get | update | delete | pause | resume | check | list-items | test | item-draft-content`. The session twins (`postFeedsAPIs`, `broadcast` permission) call the same `postFeedOperations`. In a trial-expired workspace create, update, resume, run now and preview are refused (403 `trialExpired`); list, get, items, pause and delete stay open (`POST .../pause` is on the gate's allow-list). `queue` mode publishes without review: the page says so.
- **Open.** WebSub and OAuth-protected feeds are out of scope; `signatureId` is in the API but the page has no signature picker yet; AI writing makes ONE shared text (no per-network versions: a feed with `aiWrite` ignores `templatesByProvider`, the rendered shared template is its brief) and never looks at the picture; no notification when a feed reaches `error` (the member push settings would need a new `feedPaused` type; the badge and error text on the Feeds page are the only signal); the XML decoder reads UTF-8 only (a feed in another encoding is read as UTF-8).

### Dynamic content (template language, pictures, filters)

- **Template language (`templateSyntax = v2`).** An own small language in `@chatbotx.io/utils/feed-template` (pure, no dependency, Edge-safe; parse and render are separate): `{{ path | filter: arg, arg }}` and `{{#if cond}}...{{else}}...{{/if}}` where `cond` is a path, `not path`, or `path contains "x"` / `== "x"` / `!= "x"` (case-insensitive `contains` on text and lists). No loops, includes or functions; only the documented blocks and filters exist, anything else is a parse error with its 1-based line and column (`FeedTemplateError`, API 422 `templateInvalid` with `data.line`, `data.column`, `data.code`, `data.field`). Reads are own-property only on null-prototype data (`__proto__`, `constructor`, `prototype` are refused at parse time). Caps: 5000 characters, 300 nodes, nesting 4, 8 filters per tag, 20,000 characters of output, 100 ms per render. Variables: `title link summary content author categories date image feed.title feed.link site raw["key"]`; a missing one is empty. Filters: `truncate: N` (word-safe, ends with an ellipsis), `hashtags: N` (each category to `#CamelCase`, letters of every script kept, no repeats, digits-only dropped), `date: "%d/%m/%Y"` (`%Y %y %m %d %e %H %M %S %B %b %A %a`, in the workspace time zone), `default: "x"`, `strip_html`, `upcase`, `downcase`, `capitalize`, `replace: "a", "b"`, `remove_utm`, `first`, `last`, `join: ", "`, `size`. The rendered text is plain text: control characters removed, at most one blank line in a row. A v2 result is never cut to a length: the publishing rules (`normalisePublishTarget`) decide when the post is created and a post that does not fit is recorded `skippedInvalid`, not shortened. A v2 template containing only the old `{title}` tokens is refused on save (it would be posted literally).
- **Legacy templates.** `templateSyntax = legacy` rows render with the old `{title}` `{link}` `{summary}` replacement exactly as before. Saving other settings, or a template without stating the syntax, never changes it; the owner upgrades by saving the converted template with `templateSyntax: "v2"` (the page has a Convert button; `convertLegacyTemplate` in the template package). Moving to v2 without sending the template is refused.
- **Item fields (`raw`).** `parse.ts` keeps XML namespace prefixes (`removeNSPrefix: false`) and flattens every element and attribute of an item to plain text under a versioned key format (`FEED_FIELD_FORMAT_VERSION = 1`, `fields.ts`): element path below the item with `/`, each step as written (`dc:creator`, `media:group/media:content`); first element of a name bare, repeats `name[1]`, `name[2]`, the list of a repeating name `name[]`; attributes `key@attr` (`enclosure@url`). Values are trimmed plain text (markup and entities removed, never HTML), at most 2048 characters, empty ones left out; at most 100 keys, 24 KB, depth 4, key length 120, lists of 20. JSON Feed items use the same format (property paths). The preview returns the fields of real items; the page's "Insert field" menu is built from them.
- **Picture candidates**, best first: an image enclosure (RSS `enclosure`, Atom `rel=enclosure`), `media:content` (also inside `media:group`; `medium=image` or an image type, or an image extension when neither is given), `media:thumbnail`, `itunes:image`, the first `<img>` of the content or description (resolved against the item link, tracking pixels of 2 px or less and pixel-like names skipped), JSON Feed `image` / `banner_image` / first `<img>` of `content_html`; http(s) only, repeats dropped, at most 8. `mediaMode`: `auto` uses them, `field` takes the address rendered by the `mediaField` template (first line, http(s)), `none` attaches nothing; `mediaLibraryFileIds` (at most 10 images of the workspace, picked by item key) are the fallback when none can be used. `requireImage` in the filters means the item names a picture (a candidate or a field address); whether it can be imported is only known later.
- **Importing a picture (worker and Send test).** Done BEFORE the ledger and post transaction, so no download happens while it is open. `net/feed-image-import.ts` + `net/safe-image.ts` (Node-only, own package subpaths, registered by the worker and the builder's route handlers, never in the router graph, invariant 25): https only (an `http` address is first tried over https, the plain request is made only when that fails), `checkSsrfSafety` and the pinned socket for EVERY hop, at most 2 redirects, 10 s, the body streamed and aborted past 8 MB. Before decoding: the magic bytes decide the type (JPEG, PNG, WebP, GIF; `Content-Type` and the name are never trusted; SVG, HTML and anything else are `notAnImage`), the header is read with `image-size` and a picture over 6000 px on a side or 36 megapixels is `tooManyPixels`. Then sharp RE-ENCODES it (`failOn: error`, `limitInputPixels`, `sequentialRead`, first frame of a GIF, orientation applied, metadata removed, at most 2048 px on the long side, JPEG or PNG when it has transparency; no process-wide sharp setting is changed, the runner imports one picture at a time), so anything that is not pixels does not survive; the result is stored with its correct content type. No new dependency. Budgets per run: `2 x maxItemsPerRun` attempts and 3 per host. The stored object has a STABLE path per feed and item (`media-library/feed-<feedId>-<hash of itemKey>`): a retry finds the file and reuses its Media Library id, so the post's idempotency hash does not change; a file this run created is removed when the transaction fails or the item is skipped; when two workers race (a lease expiring) the winner's post uses the stable file and the file is kept. Discarding is race-free and removes only the Media Library ROW: one transaction locks the row `FOR UPDATE`, checks `SocialPostMedia` / `SocialPostTargetMedia` for a reference and deletes the row only when there is none; a concurrent post insert takes a `FOR KEY SHARE` lock on the row through the foreign key, so it either commits first (the file is kept) or fails the foreign key and that run retries. The storage object at a stable feed path is never deleted on discard: the retry re-uses or overwrites it, so an orphaned object is bounded (at most one per item) and self-healing. Only a Send-test picture (its own random `-test-<id>` path, never shared) has its object deleted, after the commit. A failure never blocks the post: the ledger row gets `imageError` (`notHttps`, `blocked`, `unreachable`, `timeout`, `tooLarge`, `tooManyPixels`, `notAnImage`, `unsupported`, `decodeFailed`, `budget`, `storage`) and the `postAs` fallback applies (note `imageFailed`). No shared aspect-ratio or minimum-size validator exists (the publishing rules check type, size and count only, see "Unverified"), so none is promised here either. The picture's alt text is the item's title.
- **Post shape and destinations.** `postAs`: `photo` attaches the picture, `link` sends `linkUrl` = the item link (the link is removed from the text when the template put it there; networks without link posts get it appended by the rules), `text` is text only. With `photo` and no usable picture `noImageFallback` is `link`, `text` or `skip` (`skippedNoImage`, reason `noImage`). A post shares its files across its destinations, so a destination whose network cannot carry the shape (read from `POST_PUBLISHING_RULES`: a picture needs an enabled `image` type, text or link needs `text` or `link`; today Instagram needs a picture and TikTok takes video only, so it is always left out) is DROPPED from THAT item's post, listed in the ledger's `droppedDestinationIds` (note `droppedTargets`); when none is left the item is recorded (`skippedNoImage` when the missing picture was the cause, else `skippedInvalid` with reason `noDestinationAccepts`).
- **Filters.** `filters` = `includeAny`, `excludeAny`, `categoriesAny` (up to 20 terms of 100 characters each), `requireImage`, `maxAgeHours` (1 to 168). Terms match title, summary and categories ignoring case and diacritics (`Đà Nẵng` matches `da nang`); `categoriesAny` matches the categories only. Applied BEFORE the per-run limit and the daily cap, so a dropped item never takes a slot; a dropped item is recorded for good as `skippedFiltered` (reason `excludedKeyword`, `missingKeyword`, `category`, `noImage`, `tooOldForFilter`, `undatedForFilter`), so changing the filters later does not bring old items back. `maxAgeHours`: an undated item fails it, one dated in the future counts as just published. The first check applies them to the item `postLatestOnFirstCheck` would post.
- **Preview and Send test (parity).** `POST /v1/post-feeds/preview` and the feed form call the same functions the worker uses (`feedTemplateData`, `renderFeedTemplate`, `resolveFeedShape`, `partitionDestinations`, `evaluateItemFilters`, `normalisePublishTarget`) and report, per item, the text, the characters and rule issues per network, the pictures, the destinations that would be dropped and the filter verdict; `templateProblem` carries line and column. It is advisory: nothing is downloaded or stored, and creation re-validates through `createInTx`. "Send test" runs the same `prepareFeedPost` as a check (including the picture import) and saves a draft.
- **Provenance.** The Items list shows, per item, the picture's source (`enclosure`, `mediaContent`, `mediaThumbnail`, `itunesImage`, `contentImage`, `jsonFeed`, `field`, `library`, `article`), why a picture failed (including `articleUnreachable` and `articleNoImage` for the article page) and how many destinations were left out; every note of `reason` is shown. Policy for a source item edited after it was first seen: the FIRST observation wins (the ledger keeps the first title, link and picture; nothing is re-posted or updated). "Create post" from an item re-reads it, so its text uses the item as it is now. Deleting a Media Library picture a feed still lists is harmless: it is skipped at use. Not done: template history, a notification when a feed reaches `error`, per-network templates and article `og:image` fetching (phase 2).

- **Last check summary and stale copies.** Every check ends with `logger.info` "social-post feed: check finished" (feed, kind, items, fresh, eligible, created, skipped, refused, deferred, stale) and stores a compact `lastRunSummary` on the feed (also on the API resource and DTO), so "nothing happened" is visible: the Feeds table shows "No new items in the feed", "{n} posts made", "{n} items refused by a network", "{n} new items wait for the next check" or "The source has not changed". The worker's `post-publish` job logs the result of each feed job too. A CDN may serve an OLDER copy of the source: when the newest `publishedAt` of the fetched items is older than the newest the ledger has seen (`socialPostFeedRepository.maxPublishedAt`, scoped by `feedId` and `workspaceId`; only ledger rows written since the feed's `startedAt`, which an address change resets, and no date after the check's own time, so a past address or a future-dated item never makes copies look stale), the copy is stale: nothing is written (no ledger row, no post), the validators of that copy are NOT stored (so the next check cannot be answered 304 from it), `nextCheckAt` is set about 2 minutes ahead, `consecutiveFailures`, `lastErrorCode` and `status` are left as they were (a stale copy is neither a success nor a failure), the result is `kind: "stale"` and the summary says so (the page shows "The source returned an older copy; checking again soon"). At most 3 early re-checks in a row (`staleRetries`); after them the copy is taken as the truth (the source may have removed its newest items on purpose) and the normal interval applies. A copy with no dates, or a feed that has not been primed, is never stale.
- **Different text per network (`templatesByProvider`).** An optional strict record keyed by the provider enum (`facebook`, `instagram`, `threads`, `tiktok`; any other key is a 422 `validation`), each value a `v2` template of at most 5000 characters in the same language, rendered with the same data, signature and limits. A destination uses its network's template when one is set, else the shared `textTemplate`. A legacy feed cannot have any (422 on `templatesByProvider`; a v2 feed that has some cannot move to `legacy` until they are cleared); a template that does not parse is 422 `templateInvalid` with `data.field` `templatesByProvider.<network>` and its line and column. `prepareFeedPost` renders each distinct network of the kept destinations once and gives a target its own `text` (the existing per-target text) ONLY when it differs from the shared text, so a feed without network templates creates exactly the posts it always did and the idempotency hash stays a function of the item and the configuration. Several destinations of one network share its text. A network whose own text renders to nothing is left out of THAT item's post and listed in `droppedDestinationIds` (note `droppedTargets`); a network template that cannot render records the item as `templateError`. The final authority stays `normalisePublishTarget` in `createInTx`: a text a network refuses is recorded `skippedInvalid`, never shortened. **AI**: an `aiWrite` post is ONE shared text for every network (v1): the rendered shared template is the brief, network templates are not used for AI-written posts, and when the AI falls back to the template the network texts apply. The preview returns, per item, `render.providerTexts` (what each network that has a template renders, or its `templateProblem`) and per network `text` / `usesOwnTemplate` with the characters and rule issues computed on that text; the form shows them as tabs (Shared, Facebook, Instagram, Threads, TikTok) in a collapsible "Different text per network" section. Feeds are not template-copied (invariant 27), so no template adapter changes.
- **Article picture (`fetchArticleImage`).** Default false. When on and an item names NO picture candidate (and `mediaMode` is not `none`, `postAs` is `photo`), the item's link is fetched once and its `og:image` (`og:image:secure_url`, `og:image:url`, `twitter:image`, `twitter:image:src`, in that order) is imported through the normal picture path. Only for an item about to be posted: it runs inside `prepareFeedPost`, after the filters, the per-check limit and the daily cap, never for a skipped item, and `requireImage` looks only at the feed's own pictures. `net/feed-article-image.ts` (Node-only, own subpath, registered with `registerFeedArticleImageFinder` by the worker and the builder's route handlers, invariant 25): `checkSsrfSafety` and the pinned socket (`pinnedGet`) for every hop, https only (an `http` link is tried over https first), at most 2 redirects, 10 s, no cookies or credentials (only `accept` and `user-agent` are sent), a non-HTML answer is refused, at most 1 MB read and reading stops at the end of the head. The head is scanned by `findArticleImageUrl` (`article-meta.ts`): one bounded left-to-right scan over `<meta>` tags with a quote-aware attribute reader (no backtracking pattern, at most 400 tags of 4096 characters), relative addresses are resolved against the FINAL page address and only http(s) results are kept. Budgets (`ImageBudget`): at most `maxItemsPerRun` article reads per check (Send test: 1) and 3 attempts per host in all (shared with picture downloads). A failure never blocks the post: the ledger row records `imageError` (`articleUnreachable`, `articleNoImage`, `blocked`, `timeout`, `budget`, or the import error of the picture) and the feed's `noImageFallback` applies. Negative cache: every item that is processed gets a ledger row (created or skipped) carrying that error, and an item is never processed twice, so a page that failed is not fetched again; only a crashed or retried transaction refetches, and an already stored stable-path file is reused without reading the page again (the ledger retention keeps this for 180 days). The preview only flags `articleImageWillBeTried`; it downloads nothing. Provenance: `imageSource` `article`, `imageUrl` the og:image address.

## Realtime and notifications

- **Realtime event `socialPostChanged`** (workspace broadcast, `{ socialPostId, targetId?, status }`, ids and a status only). Emitted after the write has committed, best effort: a Redis failure is logged and never fails the write. Sources: a target result stored by the publisher (`published`, `failed`, `needsReview`, `processing`, and a retry as `pending`; announced from `settle` in `publish.service.ts`, only when the lease-fenced write succeeded), publish now, retry, resolve, and, from `socialPostOperations`, create, update, reschedule, duplicate and delete (`status: "deleted"` for a draft removed or a schedule cancelled). Changes made by background scans that are not a publish result (the missed-schedule scan, recurrence) do not emit.
- **Client**: `SocialPostsRealtimeSync` (mounted once by the Posts layout) calls `useSocialPostRealtimeSync`, which debounces and invalidates the list (the calendar pages through the same procedure) and the get queries.
- **Publishing connection push** (`publishConnection`): members with the Posts permission are told when a destination stops publishing: the inbox token was rejected (`publishTokenRejected`) or a TikTok login needs reauth (`needsReconnect`), a publishing permission is missing (`permissionMissing`), or the circuit breaker paused it for the network's limits (`paused`). Queue `notification`, job `notifyPublishConnection`, job id `publish-connection-<alert>-<destinationOrAccountId>-<transition>` (the rejected token's fingerprint, the pause's end), enqueued only when the conditional write really changed the row, so a recovery that records the same failure again pushes once. The handler skips when the connection recovered before it ran. Member setting `notificationTypes.publishConnection` (default off on rows stored before it existed; on for new members and owners, off for the support access membership; toggle in the member settings).
- **Push** only for `postFailed` and `postNeedsReview`: queue `notification`, jobs `notifyPostFailed` / `notifyPostNeedsReview`, job id `social-post-<action>-<targetId>-<attempt>`, so a recovery that stores the same result again pushes once. Recipients: members with that member notification type on AND the Posts page permission (`broadcast`; super admins have it). Member rows stored before these two keys existed have none, which counts as off (the schema defaults them to `false` on parse; no backfill). New members and workspace owners get both on; the support access membership gets both off. The handler skips when the target is no longer in the status the push is about (retried or resolved meanwhile) or the post was deleted.
- Not available: event emails, an in-app notification list.

## Post analytics

Growth over time of a post's platform counts (comments, reactions, shares, engagement = their sum, views). The platforms only give lifetime totals, so the daily growth comes from our own snapshots, taken by the post sync.

### Data

| Table | Role |
|---|---|
| `ChannelPostMetricDaily` | One row per post per workspace-local day on which a count was observed to change (sparse). Cumulative `commentsCount` / `reactionsCount` / `sharesCount` / `engagementCount` / `viewsCount` (bigint, **NULL = never reported**, not zero) and the signed gain of the day (`...Gain`, default 0, may be negative). `isBaseline` marks the day the post was first seen. PK `(workspaceId, day, channelPostId)`, plus `(workspaceId, channelPostId, day)` and `(workspaceId, inboxId, day)`. No foreign keys. RANGE-partitioned by month on `day` (DEFAULT partition + months created ahead). Not copied by templates. |
| `ChannelPost.metricsKnownMask` | Which of comments (1), reactions (2), shares (4) a listing ever reported for the post, plus bit 8 (`commentsTotalCurrent`) set together with the comments bit by every write that reports a comments total under the current definition (replies included where the platform counts them); display and filters read the comments bit only (views are known when `viewsCount` is not null). `ChannelPost` stores an unreported count as 0, so this mask is what tells unknown from zero. Counts and views are bigint. |

The partition clause, the DEFAULT partition and the first months are hand-written in `add_posts_management` (drizzle-kit cannot express partitioning, same as `ContactActiveHourly` and `LeaderboardScoreEvent`).

### How a snapshot is written

`upsertListedChannelPosts` writes it in the same transaction as the post upsert (so a snapshot never disagrees with the stored count): a **new** post is inserted together with its first snapshot row in one statement; for a post that **already exists** the row is computed from the locked row just before the update. Only posts published within the last 90 days are snapshotted. The day is the observation's date in the workspace time zone (read once per job; a zone change keeps old buckets).

- **Comment total definition.** A comments gain (and the comments part of the engagement gain) is a difference only when the PREVIOUS row already carried bit 8; a row measured before the comment total started counting replies is treated as newly known (gain 0), so the first read after the definition changed is a baseline, never a fake gain, with no data update of existing rows. Every platform metrics write (listing, metrics-only, single-post refresh) sets bit 8 with the comments bit, for every channel (harmless where unused). Whether a comments gain also REQUIRES bit 8 on the previous row is decided in TypeScript from the channel capability `commentTotalRebaseline` (`POST_CHANNEL_CAPABILITIES`; true for Messenger only) and sent to the SQL as a bound parameter, so a channel whose total did not change keeps its real gain; the Threads webhook increment sets it too and writes no snapshot.
- **Baseline.** The first observation of a post only seeds a baseline (gain 0, `isBaseline`), so the whole lifetime total is never one day's gain. A bare row recorded from a comment (`metricsFetchedAt IS NULL`), a row that predates the mask, and a count that becomes known later are all handled the same way, per count. A new post first seen within 48 hours of its publication counts its first total as that day's gain, and so does a bare row (composer or comment path, `metricsFetchedAt IS NULL`) that is first listed within 48 hours of its publication (gain = the reported value, `isBaseline` false); an older bare row only seeds a baseline. The snapshot day is computed in JS from the workspace zone (a zone PostgreSQL does not know falls back to the Intl-validated name, never to a `pg_timezone_names` scan).
- **Gain** = reported - stored, per count, under the row lock, only when the count was already known and the listing reports it again. An unreported count writes NULL cumulative and gain 0, never a negative number made of an unknown. Same-day observations add up (the cumulative follows the latest one).
- **Stale writes.** A write whose observation time (`observedAt`, taken before the channel was read) is not newer than the stored `metricsFetchedAt` changes nothing: a slow unfenced one-post refresh cannot overwrite newer metrics. (An unchanged post is not rewritten, so the guard compares with the last change; a slow reader that straddles an unchanged observation can in rare cases still apply one older value that differs, which the next sync corrects.)
- `backfillCompletedAt` is set only when the listing reached its end. A cycle stopped by the 2,000-post cap (`capped` outcome) is not a finished backfill.

### Fresh counts on view

Where a post's comment count comes from is a per-channel capability, `POST_CHANNEL_CAPABILITIES[channel].commentCountSource` (`platform` | `webhook`, `packages/utils/src/channel.ts`); shared code never branches on a channel name.

| Channel | Comment count | Reactions / shares |
|---|---|---|
| Messenger (Facebook Pages) | `platform` (listing, single read, batch read; replies included) | platform |
| Instagram (both logins) | `platform` (`comments_count`) | platform (`like_count`) |
| TikTok | `platform` (`comment_count`) | platform |
| Threads | `webhook` (the API reports counts only through Insights, a permission we do not request) | not reported (unknown, never zero) |

A `platform` count comes only from a read; a webhook never changes it. A `webhook` count (Threads) is kept by ChatbotX:

- **What counts.** Every NEW stored comment of the channel, replies to replies included: the Threads reply webhook names the root post (`root_post.id`), which is the id the comment path resolves, so the count is of the whole thread, not of direct replies. The comment path calls `channelPostService.recordWebhookComment` right after the comment is saved (for every delivery, redelivery included): the post is resolved first (created bare when this is its first comment), then an atomic set-if-not-set mark on the stored comment (`attributes.commentCounted`, the same mechanism as the phone count) decides whether this call counts, then ONE `UPDATE` raises `commentsCount` and `engagementCount` by 1 and sets the comments bit of `metricsKnownMask` (an unknown count becomes known). Best effort: a failure is logged and never fails the comment job; a failure before the mark leaves the comment uncounted so a retry counts it, one between the mark and the update leaves the count one short, never over. The order and behaviour of the other steps (leaderboard, automations, triggers) is unchanged.
- **Platform reads leave it alone.** The Threads listing reports `commentsCount: null`, and the write path keeps the stored value for a count the read leaves out and only ever adds bits to `metricsKnownMask`, so the sync, a refresh and the refresh button never reset a webhook count to null or 0.
- **Starts at connection.** Only comments that arrive while the inbox is connected are counted: the comments a post had before are not. A reply by the post's own author is not delivered (the webhook handler drops it), so it is not counted either.
- **Deleted comments are not subtracted.** The Threads `moderate` topic documents a `delete` field for posts the authenticated user deleted and no reply-specific delete event, so the count only goes up.
- **Scope.** This is the post counter only. Contact-level post tracking (`ContactInboxPost`, post-comment triggers, the `commentedOnPost` filter, per-post comment settings) is NOT extended to Threads (`postTrackingChannels` is unchanged); a Threads post that has comments but no tracked commenter lists through the comment count. The daily snapshots (`ChannelPostMetricDaily`) are written by platform reads only, so a webhook count is not in the analytics history.


- **Facebook comments include replies.** The comments summary is requested as `comments.limit(0).summary(true).filter(stream)` in the listing and the single-post read. The Graph comments edge documents `filter` as `toplevel` ("the default": comments made directly on the post) or `stream` (comments at all levels in chronological order), so without `filter(stream)` the total leaves replies out.
- **Batch read.** The optional `post` handler `getPostsMetrics({ postIds })` returns `{ externalPostId, commentsCount, reactionsCount, sharesCount, viewsCount }[]` with the listing's meaning of `null` (unknown, never zero). Messenger answers a batch of up to 50 posts with ONE Graph batch call (`POST /` with `batch=[{method: GET, relative_url: <id>?fields=...}]`; Graph's batch limit is 50 requests). Graph's multiple-ID read (`?ids=a,b`) is deliberately not used: Meta dropped it in Graph API v26.0 and no new app may use it (v27.0 announcement). Instagram (both logins) reads the posts one by one with the single-media read, bounded to the batch. Threads and TikTok have no batch read and are skipped. A post the channel does not answer for (gone, hidden, a failed sub-read, a timeout) is absent from the result: its counts stay and it is never marked removed; an account-wide failure (auth, permission, rate limit) is thrown and ends the job.
- **Request.** `POST /v1/channel-posts/management/refresh-metrics` (scope `posts`, CLI `channel-posts refresh-metrics`, hidden from MCP by default; private twin `privateRefreshChannelPostMetricsAPI`) takes `{ ids: 1..50 }` and `channelPostMetricsRefreshService.requestMetricsRefresh` answers `{ queued, fresh, skipped }`. It loads only the workspace's own posts, leaves out removed posts, posts whose inbox is not eligible (`postSyncEligible`) and channels without the capability `metricsBatchRead` (`skipped`), and posts whose `metricsFetchedAt` is newer than `CHANNEL_POST_METRICS_STALE_MS` (5 minutes, `fresh`). Each remaining post is CLAIMED before anything is queued: `casStore.setIfAbsent("channel-post-metrics-claim:<workspaceId>:<postId>", 1, 5 min)`. Only the request that wins a post's claim reads it, so overlapping requests ([A,B], [A,C], [A,B,C]) never read a post twice in a window (Meta counts every batch sub-request); a post whose claim is held, or whose claim failed (Redis down), counts as `fresh`. The claimed posts are grouped by inbox and queued as ONE `refreshChannelPostMetrics` low job per inbox (a generated job id, since the per-post claims already keep two jobs from sharing a post; kept 60 seconds); if the enqueue fails the claims are released. Refused on a trial-expired workspace like every POST mutation; the page does not call it when the workspace is read-only.
- **Job.** `refreshChannelPostMetrics` (`attempts: 1`, behind `withBlockedOwnerGuard`) resolves the inbox integration, takes `observedAt` before the read, calls `getPostsMetrics` and writes through the same fenced path as the sync, in the `metricsOnly` mode of `upsertListedChannelPosts`: it creates no post and writes only `commentsCount`, `reactionsCount`, `sharesCount`, `viewsCount`, `engagementCount`, `metricsKnownMask` and `metricsFetchedAt`. `metadataFetchedAt`, `removedAt`, the live columns and the description columns are untouched, so a post whose metadata fetch failed is still retried by the comment path. The observation-time guard and the daily snapshot are the same as the sync's. The full listing mode fences only the count columns, the known mask, the engagement total and `metricsFetchedAt` by the observation time; the columns only a listing reports (caption, media type, permalink, publication time, content type, author, `metadataFetchedAt`, removal recovery) are written even when a newer metrics-only read advanced the fence (the live columns keep their own `liveStatusObservedAt` fence). The description columns are fenced by `metadataFetchedAt` (a metrics-only read never writes it), which a listing stamps with its OBSERVATION time (insert, first fill and `GREATEST`), so an older listing landing after a newer one keeps the newer text and a column that is still empty is always filled. In this mode `metricsFetchedAt` advances on EVERY accepted newer read, changed or not (it is the observation fence, so an unchanged read also fences out an older delayed one and the post counts as fresh for 5 minutes); the listing mode still rewrites an unchanged post only when something changed. The snapshot rules that read `metricsFetchedAt` (a bare row has it NULL and only seeds a baseline, or counts the first total as the day's gain within 48 hours of publication) run before the update from the locked row, so they see the previous value. A failure is logged and ends the job (no retry); it then emits `socialPostChanged` with an empty `socialPostId` and status `metricsRefreshed`, the realtime event the Posts pages already refetch the list on.
- **Page.** The "On channels" list asks once per visible post per 5 minutes per tab (`useRefreshVisiblePostMetrics`, debounced, at most 50 ids per request); no spinner, no message.
- **New post from a comment.** When the comment path creates the `ChannelPost` row (first comment on an unknown post) it queues the same refresh for that one post, best effort (a failure is logged and never fails the comment job).

### Retention and purge

`maintainChannelPostMetricPartitions` (schedule queue, daily 01:40) creates the PREVIOUS month, the current month and two ahead (each create in its own try/catch, so a failing month never skips the others or the retention) and drops, by detaching the whole partition, every month entirely older than 25 months (a plain `DETACH PARTITION` in one transaction with a 10 s lock timeout, because `DETACH ... CONCURRENTLY` is not available while a DEFAULT partition exists; if writers hold the table too long the drop fails and the next daily run retries); rows still in the DEFAULT partition are then healed (every older month inside the retention gets its partition; rows of days past the retention are deleted) and, if any remain, logged as a warning on every run. PostgreSQL refuses to create a partition while DEFAULT holds rows of that month, so a create first heals it: in one transaction with a 10 s lock timeout and a 60 s statement timeout it locks the PARENT table (`ACCESS EXCLUSIVE`; locking DEFAULT first and the parent second could deadlock against an `INSERT ... ON CONFLICT`), moves that month's rows into a temporary table (`DELETE ... RETURNING`), creates the partition and inserts the rows back (now routed into it); a failure rolls everything back and the next run retries. Workspace purge drains the table by `workspaceId` in the `partitioned` stage before the workspace is deleted (AGENTS.md invariants 22/24).

### Reads

All reads are workspace-scoped, bounded (a range of at most 366 days, at most 50 top posts, at most 50 groups, a sample of at most 5,000 posts for best times, at most 20,000 posts for coverage) and use the primary key or the two secondary indexes (an EXPLAIN test pins it). Days are workspace-local `YYYY-MM-DD`; the response echoes `timezone`, and the summary also returns `today` (the workspace's current day, which the page clamps its date picker to). Local-day filters on posts are turned into timestamptz bounds in JS (`fromZonedTime`) and compared against `COALESCE(publishedAt, createdAt)`, the expression of the `sortAt` index, so they are index-friendly and a zone PostgreSQL does not know cannot fail a read. Gains already happened: a post removed later still counts in a summary or chart; only the top-posts ranking leaves removed posts out. All the request schemas are strict (an unknown key such as `channel` is a 400).

- `coverage` on the summary only (it is the one heavy read and the page uses just that one; the other reads point to the summary): `level` `none` / `partial` / `full`, how many live posts of the last 90 days exist, were measured (at least one snapshot) and have history (a baseline and a later observation, or a real gain), per channel, and `trackingSince` (first day with a snapshot). Empty or partial data is never presented as complete; a count the platform never reported has `available: false` and is not a zero. Availability comes from the posts (`metricsKnownMask`, `viewsCount IS NOT NULL`), not from the sparse snapshots: a quiet window of a reported count is 0, never "not reported". A per-post report likewise takes `available` from the post and `total` from the latest snapshot on or before the range end (not bounded by its start), falling back to the post's current count.
- **Best posting time** is the median, per weekday x hour slot in the workspace time zone, of each post's engagement relative to the median of its inbox, from posts published between 90 and 3 days ago. A slot needs 3 posts and the whole sample 20, otherwise `status: insufficientData`. Pure function `packages/utils/src/post-best-times.ts`. Nothing is applied automatically.
- Not collected yet (phase 2, needs app review and new permissions): platform insights (reach, impressions, saves). The model is ready for them (nullable counts, the mask), but no permission is requested and no insights job exists.
